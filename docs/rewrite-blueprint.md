### 0.1 产品终局（全篇的靶子）

**一句话**：一个自己掌控数据的钱包式个人财务工具——数据以加密文件的形式躺在你自己的网盘 / NAS 上，手机和电脑都能记账、都能看数，两端最终一致，没有账号、没有服务器、没有云厂商。

```
        ┌──────────────── 用户自己的设备 ────────────────┐
        │  PC（主）                      手机（副）        │
        │  记账 · 报表 · 预算 · 投资     记账 · 速览 · 拍照 │
        │       ↕                          ↕              │
        │        加密账本文件（自己选网盘 / NAS）          │
        └─────────────────────────────────────────────────┘
                    数据在用户手上，钥匙也在用户手上
```

四条产品承诺（决定架构取舍时以此为准）：

| # | 承诺 | 含义 | 对架构的强制要求 |
|---|---|---|---|
| 1 | **数据在用户手上** | 任何时候能用标准工具读出全量账目，不被任何服务锁定 | 导出格式长期稳定；加密容器格式公开可解 |
| 2 | **密钥在用户手上** | 用户自己定密钥；换设备靠恢复码，不需要任何人找回 | 恢复码必须能独立恢复全部数据；无后门 |
| 3 | **两端数字一致** | 手机记的账，电脑上立刻看得到；反之亦然 | 同步必须可重放验证（不变量 7） |
| 4 | **不依赖服务存活** | 厂商倒闭、账号被封、网盘限流，都不影响本地记账 | 离线优先；同步是后台增强，失败可见但绝不阻塞 |

**终局形态的完整清单**，以及它落在哪里：

| 能力 | 落在哪 |
|---|---|
| 周期交易 · 标签 · 多账本 · 目标储蓄 · 票据附件 · 按范围备份 | 批次 K（PC 产品补全） |
| 桌面安装包（Tauri） | 批次 K8 |
| 端到端加密同步 · 加密账本容器 | 批次 F（地基）+ G（S0/S1） |
| Android 端 · 通知自动记账 | 批次 H + I |
| 多语言 | 批次 J1（文案目录从批次 F 起随做随建） |
| 用户层面对账 · 分账 | §5.4 候选池（触发条件出现才立项） |
| 共享账本 · 多币种 · 复式记账 | §5.4 候选池（会推翻大量现有设计） |

### 0.2 优先级规则

**质量优先级（冲突时按此排序）**：

```
数据不丢 > 数字可信 > 可解释 > 结构清晰 > 交互顺手
```

只有当前一层的任务全部收口，才开始下一层。

**产品优先级**（决定做什么顺序）：

```
PC 可用  →  手机可用  →  两端同步  →  自动记账  →  多语言
```

- **PC 先于手机**：PC 是规则验证场与开发主场，键盘 + 大屏 + 本地数据库让调试成本最低。
- **手机先于同步**：手机没有它，同步没有意义；但反过来，**同步契约必须先定**（M3），
  否则手机端会先写出一套不兼容的数据，等于两端各改一遍。
- **同步先于自动记账**：自动记账产生的数据也必须能被同步，否则手机上自动记的账在电脑上是空的。
- **多语言最后**：它不改数据模型，只改展示层；但**边界必须现在就立**（§3.10），否则抽取成本随代码量线性上升。

**产品优先级不等于实现顺序**：产品上「手机能用」排在「同步」前，实现上「同步契约」排在「手机」前（见 §5.1）。

**提交粒度**：一次提交做**一件事**——一个功能或一次口径改造，它带来的连带代码精简
（删旧实现、删死代码、删冗余依赖、合并重复实现）属于同一件事，在同一次提交里完成。
只有当「精简」本身与本次改造无关时，才值得单独开一次提交。

## 1. 长期设计原则

1. **单一事实来源**：一笔交易对钱的影响，只由一个纯函数决定。任何其它地方都不得重新解释金额。
2. **派生值不落库**：余额、预算进度、快照链、收益率一律按需计算。落库的派生值必然出现「两个真相」。
3. **默认可解释**：任何一个展示出来的数字，都能沿着固定路径追到原始流水与口径版本。
4. **失败可见**：查询失败必须显示原因与重试，绝不退化成 0 或空列表。
5. **数据可恢复**：备份能恢复、迁移有历史、误删能撤销。三者缺一，用户就不敢托付数据。
6. **边界清晰**：每层只有一个职责方向；同一事实只在一个地方定义；文档只有一个入口。
7. **YAGNI + 复审触发**：不为假设中的未来造抽象。每条关键设计都写明「什么条件出现时才重新评估」。
8. **离线优先**：本地是事实源，同步是后台增强。任何一次同步失败都不得阻塞记账、不得改动本地数据、不得伪装成成功。

## 2. 设计不变量

任何实现都必须满足这 11 条，且每条都要有自动化测试。
测试覆盖情况见 [testing.md](testing.md) §5.1（那里是覆盖状态的唯一来源）。

**1–6 条是记账内核的不变量**，任何阶段都不得破坏；
**7–11 条是数据安全与同步的不变量**，在对应批次落地时开始覆盖。

| # | 不变量 |
|---|---|
| 1 | `期末净资产 − 期初净资产 == 净收入 − 净支出`（同期间、同口径） |
| 2 | `Σ 所有账户余额 == 净资产` |
| 3 | 任意交易：`Σ 分录.amount == 0`（复式平衡） |
| 4 | 退款：`退款后余额 == 原交易前余额`（全额退款时），且退款额 ≤ 可退余额 |
| 5 | 转账：`Δ转出 + Δ转入 == −fee` |
| 6 | 同一笔交易在余额、收支表、现金流量表、预算、投资分析中的「归属」可追溯到同一组分录 |
| 7 | 同步可重放：把全部设备的变更按确定性顺序应用到空库，得到与任一设备逐笔一致的状态（余额、报表、可退额） |
| 8 | 冲突不静默：同一实体只应用一个版本，另一版本必须留存且可见；绝不把两个版本都当交易入账 |
| 9 | 密文出端：同步文件与备份文件中没有明文账务数据，密钥/口令/恢复码不进入任何上传文件 |
| 10 | **合并与传输解耦**：同一组变更无论经由目录 / WebDAV / GitHub 哪种介质、以何种到达顺序应用，最终状态相同。合并在**记录层**做，不在文件层做 |
| 11 | **加密不降级**：账本文件（含备份、快照、同步文件）一律是密文；明文只存在于设备本地的 SQLite |

## 3. 目标架构

### 3.1 记账内核：生成器模型，不物化分录

**决策：保留「交易 → 有符号分录」这个模型，但不建 `postings` 表。**

- 分录由纯函数 `postingsOf(tx, ctx)` 生成，Σ = 0；余额、收支、现金流、预算、投资分析**最终**都是这组分录的投影。
- 交易表是唯一事实源；**分录不落库**。落库分录等于物化派生值，与原则 2 冲突，且引入「交易行与分录行不一致」这类致命风险（写路径必须双写）。
- 需要「一笔支出拆多个分类」或「审计级重建」时，再把分录物化——那时交易行退化为分组头，金额只存在于分录。该扩展点必须留在设计里，但今天不实现。

**口径规则必须能同时用于 SQL 与 JS（关键约束）**

背景：领域函数接收 `transactions: LedgerTransaction[]`，返回一个小数。这让 service 若想复用口径，就必须把整表读进内存——于是报表与预算绕过内核自己写了一份 SQL 汇总，同一口径出现两个答案。

因此口径拆成两层：
- **规则层**（纯数据/纯函数）：哪些交易类型计入、退款按哪种类型冲减、账户与分类如何匹配。规则层同时被领域层的纯函数与后端的 SQL `where` 消费——两边读同一份规则，不会分叉。
- **计算层**：在规则之上做聚合。**聚合在哪跑由数据量决定**（余额与统计在 SQL，余额计算走领域层的 `balanceBefore`），但口径只有一份。

**口径必须带版本**：分录生成器的规则会演进（口径调整、退款规则变化）。因此：

- 领域层维护 `ruleVersion`（口径版本号），写入每笔交易。
- 解释历史数字时，用**交易当时的版本**重算，而不是当前规则；否则改一次口径，历史报表就变了。
- 这条比物化分录更重要：它是「可解释」原则的技术前提。
- 规则按版本冻结成独立文件（`ledger/rules.v1.ts`），已发布的版本不再修改；
  新口径另建文件并登记，登记后不允许覆盖。

**属性测试**：用 `fast-check` 随机生成交易序列，断言 §2 的 1–6 条内核不变量。领域层是纯函数，属性测试成本极低、收益极高。

### 3.2 金额与精度：整数分端到端

| 层 | 形态 |
|---|---|
| 存储 | 整数分（SQLite INTEGER / Prisma `BigInt`） |
| 领域 | `Minor`（整数分） |
| 传输 | 整数分（JSON number） |
| 前端 | `Minor`（同一个 branded number） |
| 展示 / 文件 | 只在边界除以 100 |

**上限**：SQLite 是 64 位，但 JSON number 只有 `2^53` 精确。
传输与前端以 **9e15 分（90 万亿元）** 为上限，API 校验写死这个值；超出 64 位由存储层拒绝。
个人账本远到不了，但边界必须明确，不能靠「应该不会」。

**理由**：SQLite 没有真正的 DECIMAL，Prisma 的 `Decimal` 会落到 NUMERIC 亲和性，非整数值可能以浮点存储——这正是金额系统最经典的精度陷阱。整数分从根上消除它。

**舍入策略（必须写死）**：

- 输入金额：元字符串 → 分，**按小数点做字符串解析**（`"8.11"` → `811`），不经过 `Number(x) * 100`
  （`8.115 * 100 = 811.4999…`，浮点会在分位上制造 1 分误差）。
- 输入与导入都要求最多 2 位小数；超过就报错并列出前几行，**不静默舍入**（静默舍入等于悄悄改钱）。
- 存储与计算全程整数，不出现第二次舍入。
- **历史数据迁移**是唯一的例外：旧库里的浮点尾巴（如 `8.120000000000001`）在迁移时按 half-up 取整，
  并把「被取整的行数 / 最大偏差」写进对账报告。
- 退款金额允许任意分值（如退 33.33 元），但不得超过剩余可退金额。

### 3.3 日期与时区

- 交易日期存为 `YYYY-MM-DD` 字符串列（`occurred_on`），不存时分秒。
- `created_at/updated_at` 是时间戳，只用于审计与排序，不参与任何金额计算。
- 期间一律半开 `[start, endExclusive)`。
- 日期的语义（本地日历日、不做 UTC 转换）见 [requirements.md](requirements.md) §3.2。

### 3.4 数据模型（目标）

长期的数据模型要补齐的是**恢复能力**、**版本历史**与**可同步性**：

```text
ledgers(id, name, created_at)                                          ← 多账本（K3）
transactions(id, ledger_id, type, amount_minor, fee_minor, coupon_minor,
             occurred_on, rule_version, rev, vv, …, deleted_at)
audit_events(id, entity, entity_id, action, before_json, after_json, at)   ← 支撑撤销与「修改历史」
tags(id, name), transaction_tags(transaction_id, tag_id)                ← 标签（K2）
recurring_rules(id, ledger_id, …, next_occurrence)                      ← 周期交易（K1）
savings_goals(id, ledger_id, target_minor, deadline, …)                 ← 储蓄目标（K4）
attachments(id, entity, entity_id, blob_ref, …)                         ← 票据图片（K5）
```

要点：

- **软删除**：交易增加 `deleted_at`；所有查询默认过滤 `deleted_at IS NULL`。
  过滤必须集中在 **repository 层**，不允许各 service 各写一遍——漏一处就等于余额错一次。
- **审计事件**：所有写操作记录 before/after。撤销 = 依据审计事件反向写入，不需要额外的撤销表。
- **快照链**：继续持久化 `previous_snapshot_id` 不变（它是写入顺序的产物，不是金额派生值）；但「按日期排序推导」的规则要统一，禁止两处实现。
- **可同步字段**（F 批次落地）：所有可同步实体带 `rev`（本地修订号）与 `vv`（版本向量），
  并以客户端生成的 UUID 作主键。`vv` 存为 JSON 列即可——个人规模下设备数个位数，
  几十字节换掉「设备时钟可能偏差」这个隐患是划算的。
- **多账本**：所有业务表带 `ledger_id`，查询默认按当前账本过滤（过滤规则同样集中在 repository 层）。
- **票据图片不进主库**：只存引用与元数据，图片本体走文件存储（K5），
  否则 SQLite 会被二进制撑大，备份与同步都会变慢。

### 3.5 分层与依赖方向

```text
apps/web      →  apps/api（HTTP）
apps/api      →  app（用例/仓储端口）、domain（纯函数）、contracts（类型）、db（Prisma repository）
apps/mobile   →  app（同一套用例）、domain、contracts、sync、SQLite repository
app           →  domain、contracts（禁止 react/express/prisma/node:fs）
sync          →  domain、contracts、crypto（禁止依赖文件系统与网盘 SDK，传输由各端适配）
domain        →  无外部依赖（禁止 react/express/prisma/node:fs）
```

移动端出现后，**共享的是用例、规则、契约与同步协议，不是数据库实现**：
桌面继续用 Prisma，手机用 SQLite 插件，各自实现 `app` 的仓储端口。
`app` 与 `sync` 只在实际做移动端/同步时创建，不提前拆。

**决策：不拆 `packages/db` / `packages/ui`。**

- 真正要防的债是「service 里直接写 Prisma 查询」和「同一个控件在多处各写一遍」，
  这两件事用**应用内分层**就能解决：`apps/api/src/db/{repositories}` 与 `apps/web/src/ui/{原语}`。
- 拆成独立 workspace 包会带来构建顺序、产物发布、类型解析的额外复杂度，而收益只在「出现第二个后端消费者 / 第二个前端应用」时才兑现。
- **复审触发条件（已部分触发）**：移动端出现时只新增 `app`（用例）与 `sync`（同步协议）两个包；
  `db` 仍只服务桌面，不把 Prisma 抽成跨端包。只有出现**第二个桌面/服务端消费者**时，才把 `db` 升为独立包。

### 3.6 API 契约与错误模型

**契约**：类型唯一来源是 `packages/contracts`（TypeScript 类型 + 错误码）。
后端校验用 `apps/api/src/common/validators.ts` 的手写校验器并配测试。

**决策：REST 仍不引入 zod，但同步/备份格式必须做运行时校验。**
理由：移动端不走 REST，而是共享 `app` 与 `sync` 包，因此「第二个客户端」不会让 REST 变成 contract-first 的理由；
但同步文件来自网盘、可能跨版本，是**真正的不可信输入**，必须逐条校验并拒绝整批，不能信 TypeScript 类型。

- **复审触发条件**：出现对外开放 API 或第三个远程客户端时，REST 切换为 contract-first（zod 或 ts-rest）。
- 同步格式的校验器放在 `packages/sync`，与格式版本一起测试；不允许「先部分应用，再报错」。

**错误模型**：已定型，长期不变——判别联合响应、统一错误码、`requestId` 贯通。
规则见 [dev-guide.md](dev-guide.md) §7，此处不重复。

**分页**：保持 offset（`page` / `pageSize`）。个人账本十年内不会超过游标分页的收益区间，游标只会增加「上一页/下一页」的实现成本。
**复审触发条件**：单账户交易数超过 5 万或列表查询稳定超过 300ms 时，再评估游标或虚拟滚动。

### 3.7 前端结构

- **feature 切片**：`features/<domain>/{api,schema,hooks,components}`。
  - feature 之间**可以**互相引用，但只能通过对方的公开入口（`index.ts`），禁止深路径导入；跨 feature 依赖必须是有意的、少的。
  - `index.ts` 是 feature 的公开入口，属于「包公共入口」，不算违规的桶导出。
  - 页面（`routes/` / `pages/`）只做布局装配，业务逻辑下沉到 feature。
- **共享原语层** `apps/web/src/ui/`：只放真正被多处复用的原语（`MoneyText`、`DateField`、`PeriodPicker`、`DataTable`、`EmptyState`、`ErrorState`、`PageHeader`）与设计令牌。
  - **不做「包装层的包装层」**：只有当某个原语需要统一行为（金额等宽、日期格式、错误呈现）时才包；否则直接用 AntD。

### 3.8 信任层（数据可信度）

这是长期价值最高、当前最缺的一层。目标能力：

| 能力 | 说明 |
|---|---|
| 撤销 | 单条删除不弹确认，改为「已删除 · 撤销」；撤销基于审计事件反向写入 |
| 修改历史 | 详情页可看这笔记录的变更历史 |
| 回收站 | 软删除的交易可查、可恢复 |
| 导入回滚点 | 覆盖导入前自动快照，可一键回退 |
| 导入预览 | 导入前显示将新增/更新/跳过多少条与冲突样例 |
| 自动定时备份 | 可选开关，到点自动导出一份 |

### 3.9 运行基线

| 项 | 目标 |
|---|---|
| SQLite 参数 | 开启 WAL；设置 `busy_timeout`（≥5s）；避免读写互斥导致的「database is locked」 |
| 并发写 | 单进程内写操作串行化（写队列）；前端同一时刻只允许一个写请求在飞 |
| 性能包络 | 目标规模：10 年 × 每年 500 笔 ≈ 5000 笔交易、50 个账户；全量报表与余额计算 < 200ms，列表查询 < 100ms。**查询的扫描量必须随期间增长，不随总历史增长。** 超出包络时先测量再改结构 |
| 数据自检 | `npm run db:verify`：重算全部余额与报表，用 §2 的不变量交叉比对，输出差异报告（发现损坏、重复、口径漂移） |
| 日志分级 | 领域层错误不打 error 级；未知异常打 error 并带堆栈 |

### 3.10 多端与同步（目标）

#### 端拓扑

```text
桌面：apps/web → apps/api(HTTP) → app 用例 → Prisma/SQLite
手机：apps/mobile(Capacitor + React) → app 用例 → SQLite（手机本地）
共享：domain（算钱）· contracts（类型）· app（用例/仓储端口）· sync（加密/合并/应用）
同步：用户自己的网盘 / NAS / GitHub ↔ 加密账本容器 ↔ 每台设备的本地账本
```

- **桌面**：现有 React + Vite + Express + Prisma 全部保留，是第一客户端，也是规则验证场。
- **手机**：Capacitor + 现有 React 构建产物 + Kotlin 原生模块（通知监听、文件与密钥访问）。
  手机不跑 Express/Prisma，只实现 SQLite 仓储适配器。
  现有响应式布局先直接用；只有实测不达标时才针对屏幕引入移动控件，不整体换 UI 库。
- **iOS / iPad**：复用 UI、用例与领域层；通知自动记账**不承诺**。iPad 不是放大的手机，单独排期。
- 移动端复用现有 feature/query 层：把 `services/api.ts` 的实现换成「本地仓储适配器 + 相同的响应信封」，
  不为移动端重写一套数据流。手机数据量在 §3.9 包络内，报表直接调领域层纯函数，
  **不复制桌面端的 SQL 聚合**——规则仍只有一份。
- 如果 WebView 在某个屏幕真的顶不住（长列表、图表、后台），**按屏幕**引入 Kotlin 原生页；
  只有整个应用都顶不住时，才重新评估 React Native / 全原生。

#### 同步的三层结构

同步不是一件事，是三层。**每层能独立交付、独立验证**，且互不阻塞：

| 层 | 负责什么 | 交付物 |
|---|---|---|
| **数据层** | 哪些实体可同步；每条记录带什么版本信息 | `rev` + 版本向量 + `deletedAt` 墓碑 |
| **传输层** | 字节怎么离开设备、怎么加密 | 加密容器文件 + 介质适配器 |
| **合并层** | 两份状态怎么合成一份 | 记录级合并算法（幂等、顺序无关） |

**合并层必须与传输层解耦**（不变量 10）：目录、WebDAV、GitHub 都只是把字节送到对端的管道，
合并逻辑完全不需要知道文件从哪来。新增一种网盘不碰合并逻辑，改合并策略也不碰传输。

#### 数据层：可同步实体与记录级版本

| 实体 | 同步内容 | 注意 |
|---|---|---|
| 账户分类 / 收支分类 | 整条记录 + 树结构字段 | 分类树的父子关系随记录一起传；删除走墓碑 |
| 账户 | 整条记录 | 期初余额与期初日期是普通字段 |
| 交易 | 整条记录 + 金额/日期/类型/退款关联 | 核心实体 |
| 预算 | 整条记录 | 预算用量是派生值，不传 |
| 投资快照 | 整条记录（**前链不传**） | `previousSnapshotId` 本地按日期规则重算 |
| 变更日志 | 仅 S2 需要 | 见「同步形态的三个台阶」 |

**用版本向量（vv）判断先后，不用时间戳**。每条可同步记录带两个东西：

- `rev`：本设备对该记录的本地修订号，每次本地修改 +1。
- `vv`：版本向量 `{deviceId: maxRev}`——写这条记录时，本设备在各设备上已知的最高修订号。

合并两条同 `id` 的记录时：

1. **可比**（A 的 vv 在每一维都 ≥ B 的 vv）→ A 是 B 的后继，取 A。**与时钟无关。**
2. **不可比**（各有对方没有的修订）→ 真并发修改 → 进冲突列表，**两个版本都保留**。
3. **vv 相同且内容相同** → 幂等，丢弃副本。

为什么不用时间戳：设备时钟可能偏差几小时，用 `updatedAt` 排序会让「先写的记录被后写的覆盖」——
钱会被静默改掉，而且用户无法察觉。为什么不用 `baseRev` 兜底：`baseRev` 只在增量日志里拿得到，
快照式同步没有它。版本向量两者都能覆盖，代价是每条记录几十字节。

#### 传输层：加密容器 + 文件

**所有离开设备的字节都是加密容器**，全项目一种格式：

```text
container = header(formatVersion, ledgerId, kdf, salt, nonce) + ciphertext + tag
```

- 容器内是**记录流**：每个实体一条记录，带 `rev` / `vv` / `deletedAt`。
- 一条记录表达的是**结果状态**，不是操作指令（快照语义，不是命令语义）。
  因此同一份容器可以被重复应用、任意顺序应用，结果都一样（不变量 10）。
- AEAD：`XChaCha20-Poly1305`；AAD 绑定 `formatVersion|ledgerId`，防换头与跨账本重放。
- 密钥：`Argon2id(口令)`。**口令就是恢复码**——用户抄下来的那一串，不另设密码。
  同一账本的所有设备共用这一个口令，这是「多设备能互相解密」的前提。
  设备级独立密钥 + 共享密钥的两层结构推迟到出现共享账本时再做。
- 容器带 `formatVersion`，未知版本**拒绝整批**；坏记录不部分应用。

**加密威胁模型**：

- ✅ 防：网盘泄露、云服务商读取、传输窃听、备份文件被复制、GitHub 仓库泄露。
- ❌ 不防：设备被解锁后读取本地明文 SQLite、键盘记录、用户交出恢复码。
- 元数据仍会泄露：文件名、设备数量、文件大小、修改时间、同步频率。
  「端到端加密」不等于「什么都看不见」——设置页要写明这一点。
- 本地静态加密：当前是明文 SQLite + 操作系统磁盘加密 / 手机沙箱。
  SQLCipher 只在「设备丢失」成为真实威胁时做，且先证明迁移不丢数据。

#### 传输适配：目录 / WebDAV / NAS / GitHub

| 介质 | 怎么用 | 成本 | 说明 |
|---|---|---|---|
| **本地目录** | 读目录下所有容器文件 | 最低 | OneDrive / Dropbox / iCloud / Nextcloud 客户端的同步目录；零 API、零 OAuth，**先用它验证协议本身** |
| **NAS** | 同目录，或 WebDAV | 低 | 群晖 / 威联通 / 飞牛都支持 WebDAV 或 SMB 挂载 |
| **WebDAV** | 列举 / 下载 / 上传 | 中 | 一个适配器覆盖多数自建与商用网盘 |
| **GitHub 私有仓库** | 每次同步提交一个容器文件；拉取时下载并合并 | 中 | **只做容器搬运，不做 Git 合并**（见下） |
| **厂商 API** | 同 WebDAV 但走 OAuth | 高 | 每家一套 OAuth、配额与审核，最后才做 |

**GitHub 的定位必须说清楚**：它能当网盘用——因为合并发生在记录层，
新设备就是多读几个容器文件，不需要 Git 的分支/合并语义。
但**不要把 Git 提交当成同步协议**：不依赖行级 diff，不做 Git 层面的冲突解法。
GitHub 的额外收益是每次同步留一个历史版本，等于免费获得时间旅行备份。
它不适合作实时同步的原因是延迟与配额，而不是协议不能做。

**NAS 值得单独强调**：它是「数据在用户手上」最纯粹的形态——文件在自己的硬盘上，
不经过任何云服务商，连元数据都不外泄；局域网内同步甚至不需要公网。

#### 同步形态的三个台阶

不要一上来就做最难的。按收益/成本排序：

| 台阶 | 形态 | 用户看到什么 | 复杂度 | 什么时候做 |
|---|---|---|---|---|
| **S0 手动容器** | 「导出加密账本文件」→ 放到网盘/NAS → 另一台设备「导入」 | 能把账搬到另一台设备；丢数据能救 | 低：导出/导入 + 加密 + 合并 | M3 交付容器，M4 用它搬账 |
| **S1 自动目录同步** | 配一个目录，两端定时拉取/推送容器文件 | 两端自动收敛，不用手动 | 中：传输适配 + 合并 + 冲突界面 | M5 |
| **S2 增量变更日志** | 只传变化部分 | 大账本下传输量小 | 高：op log 落库 + `seq` 连续性 + 增量应用 | 账本 >10 万条或容器 >50MB 才做 |

**S0 就能验证最危险的部分**（加密容器格式、版本向量、合并算法、跨端测试向量），
却只花 S1 十分之一的成本。所以 S0 必须先做——它是 S1 的验收工具，不是过渡产品。
S0 拆在两个里程碑里：**M3 交付容器与合并算法**（PC 上可用、可导出可恢复），
**M4 交付跨设备搬运**（手机能装、能读桌面导出的容器）。

S2 才需要「每台设备只写自己的文件 `<ledgerId>/ops-<deviceId>.log`」这类增量日志设计：
那时才引入 `seq` 连续性检查、半写文件处理、op log 与业务写同事务落库。
在那之前，用整份容器覆盖是**更简单也更安全**的选择——不需要文件锁、不需要合并日志、
不会产生「冲突副本」，而且天然幂等。

#### 自动记账（Android 通知采集）

**承诺的是「通知辅助记账」，不是「全自动记账」。**

```text
通知 → 允许列表内的支付/银行 App → 本地解析 → 候选收件箱 → 去重 → 用户确认 → 正常交易写入
```

- 采集与账务分离：候选不是交易，不参与余额与报表；确认前不进账本。
- v1 不自动入账。按商户的学习规则，只在解析准确率被真实数据证明、且用户显式开启后才做。
- 只生成支出候选；退款/转账/收入的通知语义不可靠，不自动生成。
- 去重复用 `importKey`（`notify:<包名>:<稳定哈希>`），并与同金额、同时间附近的已有交易比对，
  避免「手动记过又自动记一遍」。
- 原始通知文本只在设备本地、只在候选期保留（默认 7 天），不进同步、不进备份、不进日志；
  只保存解析后的金额/商户/时间/来源。
- 通知可能被系统折叠、内容隐藏、App 根本不发、厂商杀后台；解析失败必须在收件箱可见，
  不能静默丢弃。Google Play 对通知监听权限有披露与审核要求，可能拒绝；sideload 是备选。
- 回退：没有权限或解析不了时，保留手动快速记账与「分享到 MoneyBrain」入口。

#### 多语言与货币边界（现在立边界，翻译后做）

**语言 ≠ 货币**：多币种估值仍是非目标；只允许账本级单币种 + 本地化显示格式。

- **现在就把边界钉死**（这部分成本低，但省不掉）：
  - 金额格式化只有一个入口（`formatMoney(minor, locale, currency)`），组件里禁止出现 `¥`、`toFixed(2)`。
  - 日期展示只有一个入口（`LocalDate` + locale）；存储永远是 `YYYY-MM-DD`。
  - 错误提示走错误码映射（已有），后端不拼用户文案。
  - **CSV / 备份 / 同步格式的键名与枚举值不本地化**，它们是机器格式；只翻译显示名。
  - 文案保持完整句子，不拼「前缀 + 名词 + 后缀」，否则翻译必然坏。
  - **分类名、账户名、备注属于用户数据，不翻译**——翻译它们等于篡改用户写的东西。

- **文案目录的落地方式**（关键决策，避免「一次性大抽取」）：
  - 建立单一文案目录 `packages/contracts/src/i18n/`，初始只含 `zh-CN` 一个 locale。
    **不上 i18n 框架**（单语言时框架是纯负担），但所有**新增或被修改**的用户可见文案
    必须先进目录，组件里不再出现裸字符串。
  - 已有的散落文案**在被触及时**（改到那个文件、那行时）顺手迁进目录，
    不做「一次性抽取全部上万字」的独立工程——那种工程会永远排不上队，
    而且抽取期间新旧两套并存，反而更容易漏。
  - 上第二种语言时 = 补一份 `en-US` 目录 + 接入一个轻量查表函数，**不改任何组件**。
    这条路径成立的前提是「组件不写裸字符串」，所以规则从今天起生效，
    而不是等到要翻译时才补——那时要改的是全部 80 多个文件，成本差一个量级。

- 触发条件：真的要上第二种语言时，一次性接入查表函数与语言切换；
  目录已经建好，那次工作量应当只有「补翻译 + 接查表」，而不是「抽上万字」。

#### 同步对现有模型的要求（M2 补齐）

| 要求 | 现状 | 动作 |
|---|---|---|
| 客户端生成 ID | Prisma `@default(uuid())`，离线创建没有 ID | 所有可同步实体由客户端生成 UUID，服务端不再代生成 |
| 修改版本 | `Transaction` 只有 `createdAt`，没有 `updatedAt`；其它表有 `updatedAt` | 所有可同步实体补 `updatedAt` + `rev` + `vv`（版本向量） |
| 删除墓碑 | 硬删除（B2 改软删除） | `deletedAt` 随记录传播；快照式同步天然携带墓碑 |
| 账本与设备标识 | 无 | `ledgerId`、`deviceId`（设备首次注册时生成并持久化） |
| 派生字段 | 投资快照 `previousSnapshotId` 落库但属于派生链 | 不写入同步记录；应用后按日期规则重算 |
| 同步排序 | 依赖时间戳 | 用版本向量判定先后，**不用设备时钟**（时钟可能偏差几小时） |

#### 这一层明确不做

自建服务器、账号体系、共享账本（多人共用一本账）、实时协作、CRDT、
把 SQLite 文件直接放网盘（会被网盘客户端写坏）、Git 层面的合并与冲突解法、
厂商 OAuth 全家桶、本地库端到端加密（本地明文是明确边界）。

**关于 GitHub**：它**是**受支持的同步介质之一（见「传输适配」表），
只是不承担「同步协议」的职责——不做 Git 分支合并、不做行级 diff。

## 4. 差距清单

每条含「现状 / 目标 / 验收」。**出口条件**：该批全部验收通过，且 §2 中相关的不变量在测试中成立
（记账内核 1–6 条在 A3 覆盖；同步相关的 7–11 条在 F/G 批次覆盖）。

**批次的执行顺序不等于排列顺序**。批次编号按「主题」分组（A 口径 / B 信任 / C 一致性 /
D 结构 / E 体验 / F 同步地基 / G 同步传输 / K PC 产品 / H 移动端 / I 自动记账 / J 按需扩展），
实际先后看 §5.1 里程碑表。关键的跨批次硬依赖有两条：

- **K1–K3 → F**：周期交易、标签、多账本决定可同步实体的集合与字段，必须先定模型。
- **F → H**：手机端必须从第一天就按同一套同步契约写，否则两端各改一遍。

### 批次 A · 口径与内核（正确性地基）

| # | 现状 | 目标 | 验收 |
|---|---|---|---|
| A0 | 清库缺单测；投资分析仍自成一套现金流口径 | 补清库单测；投资分析接入领域层规则 | 清库覆盖正常/边界/空数据；投资分析不再有第二份「转账本金」实现 |
| A3 | 不变量靠少量用例 | `fast-check` 属性测试覆盖 §2 的 1–6 条 | 随机 1000 组交易序列恒成立 |
| A4 | 收入/支出/退款的 `amount` 存净额，`fee/coupon` 冗余；转账存本金。**已评估，推迟** | 统一「本金 + 手续费」：所有类型 `amount` 都是本金，手续费独立记账，净额由服务端算 | `fee` 不再是派生字段；「我付了多少手续费」可查；表单只送本金/手续费/优惠券，**前端不再计算任何写库金额** |

**A4 为什么推迟**：核对数据后否掉了。

- 收入 `amount` 本来就是净额（本金 − fee + coupon），现有数据的收入行 `fee/coupon` 全是 0，拆开不产生任何新信息。
- 退款行没有本金/手续费拆分，只有 `relatedTransactionId` + `relatedType`；要存本金就得新增字段并回填历史。
- `remainingRefundable` 以 `amount` 为可退上限。改 `amount` 的含义会连带改变可退金额，属于账务语义变更，不是单位换算。
- 触发条件：出现「手续费需要单独统计或单独分类」的真实需求，或前端仍在计算写库金额。在那之前，A4 保持现状。

后续不得倒退的硬约束：

- **分是唯一权威单位**：每多一层单位，就多一类「把 1234 分当 1234 元」的错。
  传输也用分之后，前端不需要任何换算，也就没有换算错的可能。
- **字段名不加单位后缀**（`amount` 而不是 `amountMinor`）：单位由类型 `Minor`（branded number）保证——
  写错编译不过；后缀靠人记，漏写没人拦。反过来，**人类读的边界必须显式写单位**：
  CSV 表头、备份 manifest、UI 标签、错误信息。
- **元只出现在两个边界**：用户输入框、文件（CSV / 备份）。输入用字符串按小数位解析，
  不要 `Number(x) * 100`（`8.115 * 100 = 811.4999…`）。

## 5. 开发路线（优先级）

### 5.0 排序原则

- **先能用，再好用，再能同步**：PC 端单机可用是地基，不是可选项。
- **安全网先行**：备份可恢复 + 迁移有历史 + `db:drill`，没有它不动存储。
- **PC 端先补齐产品，再做移动端**：手机要同步的必须是一个完整产品，
  不是半个记账器。周期交易、标签、多账本这些实体必须在同步契约之前定下模型。
- **先能证明，再建传输**：合并算法先在单机证明正确，再碰网盘。
- **同步就绪契约放在 PC 阶段**（批次 F）：它只改数据模型与本地能力，不接网盘。
  等移动端写完再补，等于两端各改一遍。
- A4（净额 → 本金）已评估推迟，理由见批次 A；它不是单位问题，等真实需求出现再做。
- **每个里程碑自带清理**：本次改动产生的无用代码与文件必须当场删掉
  （见 [dev-guide.md](dev-guide.md) §5.1），不留到「以后再清」。
- 里程碑串行，但 spike 可以提前做；spike 代码不进主干，只留结论与测试向量。

### 5.1 里程碑

| 里程碑 | 优先级 | 内容 | 用户看到什么 | 出口条件 | 关键依赖 |
|---|---|---|---|---|---|
| **M0 · 单机可信** | P0（现在） | B1–B3、C1–C3、A0、A3、E1–E3 | 记账不再怕误删与覆盖导入；报表期间统一 | 覆盖导入可回退；删除可撤销；报表期间统一；不变量 1–6 在随机序列上恒成立 | — |
| **M1 · 结构收口** | P0 | D1–D7、D9、E4 | （无用户可见变化，是给后面铺路） | service 不碰 Prisma；并发写无冲突；查询量只随期间增长；repository 成为移动端可替换的缝；同类配置只有一个入口 | M0 的 B2 |
| **M2 · PC 产品完整** | P0 | K1–K8、E6 | 周期交易、标签、多账本、储蓄目标、票据、按范围备份、双击启动 | 「PC 端可用」清单全部达成（见 §5.2） | M1 |
| **M3 · 同步地基** | P1（PC） | F1–F11 | 账本能导出成一个加密文件 | 加密容器可导出可导入；版本向量合并任意顺序结果一致；备份与同步共用一套加密；容器格式可独立解密 | M1 的 D1、M2 的 K1–K3（实体集合定型） |
| **M4 · 跨设备可用** | P1 | H1–H8 + G1、G6、G7、E5（S0 手动搬账） | 手机能装；账能用文件在设备间搬 | 手机与桌面导出的容器互相可读；新设备 10 分钟恢复出同样余额 | M3 的加密容器；V2/V3 spike 通过 |
| **M5 · 自动同步** | P1 | G2–G5（S1） | 两端自动收敛，不用手动搬 | 网盘 / NAS / GitHub 任一介质都能同步；冲突可见且不重复计钱 | M4 有第二台设备 |
| **M6 · 通知自动记账** | P2 | I1–I6 | 手机自动识别消费通知 | 真机候选可解析、可确认、可去重；失败可见；原文不出设备 | M4；可晚于 M5 独立上线 |
| **M7 · 多语言与按需扩展** | P3 | J1–J4 + 文案目录接入 | 界面可切语言 | 每条独立验收 | 真的有第二种语言需求 |

**为什么 M3 在 M4 之前，却不是「先做同步」**：M3 只做数据契约与加密容器，没有网盘、没有第二台设备，
所以它仍属于 PC 阶段；它让移动端从第一天就按同一契约写，避免 M4 之后返工。
真正跨设备的同步（M5）仍在移动端之后，符合「PC → 移动端 → 同步 → 自动记账」的顺序。

**M4 的范围必须写死**：只做「手机能装 + 能用文件把账搬过去」（S0 手动搬账），
不做自动同步。四张报表、投资快照编辑、批量导入留在桌面；
手机端「功能看起来少」是刻意的，不是缺陷。

**M2 为什么排在 M3 前面**：手机端要同步的必须是一个完整产品。
先做手机端再补 PC 功能，等于手机要为一堆尚未确定的实体（周期交易、标签、多账本）
预留同步接口，模型改一次两端都要返工——这是「先 PC 后手机」最容易被低估的代价。

### 5.2 「PC 端可用」的验收清单

「M2 · PC 产品完整」的出口条件。用户能独立用 MoneyBrain PC 版完成一整年的记账，
且中途不需要开发者介入：

| # | 能力 | 验收 |
|---|---|---|
| 1 | 冷启动可用 | 新库有引导，3 步内看到非零净资产（E1） |
| 2 | 日常记账够快 | 常规记账 3 步内完成（E2） |
| 3 | 不怕误删 | 单条删除可撤销；批量/覆盖/清空有明确确认与数量（B2、E3） |
| 4 | 数据可找回 | 覆盖导入有回滚点；备份能恢复（`db:drill` 通过）（B1、B3） |
| 5 | 报表可信 | 四张报表数字自洽，对账条差额为 0（C1–C3） |
| 6 | 查得动 | 关键字搜索 + 批量操作（E3） |
| 7 | 周期事务不漏 | 周期交易自动生成待确认交易（K1） |
| 8 | 多维度归类 | 标签可筛选（K2） |
| 9 | 多本账 | 多账本可切换且独立统计（K3） |
| 10 | 攒钱看得到 | 储蓄目标进度自动算（K4） |
| 11 | 票据留痕 | 交易可附票据图片（K5） |
| 12 | 局部搬运 | 按范围备份/导出/恢复（K6） |
| 13 | 装得起来 | 桌面可一键启动（Tauri），不要求用户开终端（K8） |
| 14 | 数据能带走 | 导出格式长期稳定，能用标准工具读出全量账目；加密容器由 M3 交付（F5、F10） |

第 1–13 条是**「PC 端可用」的门槛**：装不上、启动不了、找不到数据的应用不算产品。
即使移动端与自动同步永远不做，MoneyBrain 依然是一个完整的个人财务工具。
第 13 条要在 M2 结束前落地；第 14 条的前半（M2）后半（M3）分别属于两个里程碑。

### 5.3 依赖关系

```text
M0 单机可信 ──> M1 结构收口 ──> M2 PC 产品完整 ──> M3 同步地基 ──> M4 跨设备可用 ──> M5 自动同步
                                                                       │                    │
                                                                       └──> M6 通知自动记账 ─┘
                                                                                        │
                                                                                        └──> M7 多语言
```

- **M2 → M3 是硬依赖**：K1–K3（周期交易 / 标签 / 多账本）决定可同步实体的集合与字段。
  模型定错一次，移动端与同步都要返工。
- **M3 → M4 是硬依赖**：手机端必须从第一天就按同一套容器格式与同步契约写。
- **M4 → M6**：自动记账是手机端能力，依赖手机端可用；但**不依赖 M5 自动同步**——
  自动记的账先落在手机本地，同步晚一点上线也不影响它工作。
- **M6 → M5 仍是最终要求**：手机上自动记的账要在电脑上看得到，
  所以 M5 可以晚于 M6 独立上线，但不能永远缺席。
- **M7 独立**：多语言不改数据模型，只改展示层，随时可插入。

### 5.4 候选功能池（还没立项，触发条件出现才做）

这些是「可能需要、但现在没有明确需求」的功能。**不是承诺**，是备选池。
技术方案已明确、只等触发条件的（iOS、SQLCipher、厂商 API、i18n）见批次 J。

| # | 功能 | 价值假设 | 触发条件 |
|---|---|---|---|
| P1 | 共享账本（多人一本账） | 家庭共同记账 | 单人模式被明确抱怨；需要权限模型 |

| P3 | 多币种估值 | 海外账户 | 出现真实外币账户（语言需求不算） |
| P4 | 桌面小部件 / 快捷键 | 记账频次高的用户 | 记账被高频使用（每周 >20 笔） |
| P5 | 发票 OCR | 自动填金额 | 票据功能被高频使用 |
| P6 | 复式记账（可配科目表） | 专业会计需求 | 出现明确的专业用户 |
| P7 | 现金流预测 | 提前知道够不够花 | 预算与报表被高频使用 |

| P10 | **分账**（AA 记账，一笔支出拆给多人） | 聚餐、团建等场景 | 出现多用户诉求但暂不共享账本 |

**P1/P6/P3 会推翻大量现有设计**，真要做时应当重新评估而不是直接开工。

编号用 `V`（验证），与 §5.4 候选功能池的 `P` 区分开。

### 5.6 主要风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 低端 Android 上 WebView + AntD 卡顿 | 记账体验不可用 | V2 真机实测；按屏幕降级，不整体重写 |
| 通知权限被厂商 ROM 限制 / Play 审核拒绝 | 自动记账不可用 | V4 验证；保留手动与分享回退；sideload 备选 |
| 手机/平板访问不到「已同步目录」 | 同步不可用 | WebDAV / NAS 适配器；仍不行才做厂商 API |
| 用户丢失恢复码 | 数据永久不可解 | 强制抄写 + 新设备恢复演练 + 界面明确说明无找回 |
| 冲突处理把两个版本都入账 | 重复计钱 | 不变量 8 + 专项测试；同一 `entityId` 只应用一个版本 |
| 设备时钟偏差导致覆盖错版本 | 数字被静默改掉 | 用版本向量而非时间戳排序（不变量 10） |
| 桌面与手机各写一套规则 | 数字分叉 | 共享 `app`/`domain`；跨端测试向量；合并后 `db:verify` 恒过 |
| 容器文件损坏或只同步到一半 | 数据分叉 | 逐条 AEAD + `formatVersion` 校验 + 原子重命名 + 拒绝整批应用 |
| 网盘客户端改写文件导致容器损坏 | 同步不可用 | 临时文件 + 原子改名；校验失败不应用 |
| 容器体积无界增长 | 同步变慢 | S0/S1 接受（个人规模几 MB）；>50MB 才做增量日志（S2） |
| 用户以为「端到端加密」连本地也加密 | 安全预期错误 | 威胁模型写进设置页；本地明文是明确边界 |
| Tauri 包不住 Express + Prisma | PC 端装不起来 | V1 先验证；失败回退到启动脚本 + 浏览器，不硬凑 |
| 「PC 产品完整」被拖成无底洞 | 移动端迟迟不能开始 | §5.2 清单写死范围；清单外的进 §5.4 候选池 |

每个里程碑结束都要能回答四个问题：**这笔钱在 5 个视图里是否一致？断网还能不能记账？
两台设备冲突时会不会重复计钱？换一台空设备能不能恢复出同样的余额？**

| 24 | **同步合并在记录层，不在文件层** | 合并逻辑与传输介质解耦，换网盘不改合并代码；记录层合并天然幂等、顺序无关 | 文件级合并（Git merge、文件版本 diff） | 需要增量传输且单容器 >50MB |

| 29 | **PC 产品完整先于移动端** | 手机要同步的必须是一个完整产品；周期交易/标签/多账本改变可同步实体集合，晚定模型要两端返工 | 先做手机端再补 PC 功能 | — |

## 7. 明确不做（非目标）

除非满足复审触发条件，否则不做：

- **自建服务器、账号体系、厂商托管的云同步**。同步介质是用户自己的网盘 / NAS / GitHub，
  不是我们运营的服务。
- **多人共享账本**（家庭成员共用一本账）与实时协作。
- **多币种与汇率**。
- 微服务、消息队列、独立数据库。
- 容器化部署、K8s、CI/CD 流水线（个人项目，本地跑更简单）。
- 第三方账单抓取、OCR。
- 投资实时行情接入。
- 为「将来可能」提前抽象（模型预留 ≠ UI 提前做）。

> 更远的候选（共享账本、多币种、复式记账等）见 §5.4 候选功能池，
> 它们会推翻大量现有设计，真要做时重新评估而不是直接开工。

## 8. 反模式清单

写进 code review checklist：

- ❌ 在 React 组件或 route 里算钱。
- ❌ 同一口径在两处各写一遍（SQL 一份、JS 一份），或领域函数与线上代码给出不同答案。
- ❌ 领域函数收整表数组却不给 service 留聚合路径（结果就是 service 绕过它）。
- ❌ 用浮点存金额、用带时分秒的时间存交易日期。
- ❌ 持久化余额、预算百分比、快照前链、收益率。
- ❌ 物化派生值后又手工维护两份。
- ❌ 每个 mutation 手工列 `invalidateQueries`。
- ❌ 用字符串 message 判断错误类型（必须用 `code`）。
- ❌ `res.data.data!` / `res.data.data ?? []`。
- ❌ 失败时渲染 0 或空列表。
- ❌ 跨期退款让「已用」变成负数。
- ❌ 软删除过滤散落在各 service（必须在 repository 层统一）。
- ❌ 同一概念两个名字（`flow/transaction`、`allocation/holding`）。
- ❌ `index.ts` 桶导出（feature / package 的公开入口除外）。
- ❌ 弹窗套弹窗；报表页里改配置。
- ❌ schema 变更只 `db push` 不留迁移文件。
- ❌ 备份格式不带版本号。
- ❌ 查询量随总历史增长（列表与统计必须随期间收敛）。
- ❌ **用时间戳判断两条记录谁更新**（同步场景下时钟会骗人，用版本向量）。
- ❌ **用文件级 diff 做同步合并**（合并必须在记录层，否则换介质就要重写合并逻辑）。
- ❌ **组件里写死用户可见文案**（多语言的前提是「组件不写裸字符串」）。
- ❌ **同一个东西写两份加密实现**（备份与同步必须共用一套容器格式）。
- ❌ **冲突时两个版本都入账**（同一 `entityId` 只应用一个版本，另一版进冲突列表等用户决定）。
- ❌ **把 SQLite 文件直接放网盘**（网盘客户端会写坏它；同步的是加密容器，不是数据库文件）。

## 9. 已评估但不采用的方案

保留结论，避免反复讨论；每条都写明什么条件下值得重议。

| 方案 | 结论 | 理由 | 重议条件 |
|---|---|---|---|
| 物化 `postings` 表 | ❌ 现在不做 | 物化派生值 + 双写不一致风险；收益（拆多分类、审计级重建）尚未出现 | 见决策 #2 |
| Fastify / tRPC / ts-rest 替换 Express + REST | ❌ | 现有 Express + REST 稳定；contract-first 的收益用类型契约即可拿到 | 见决策 #15 |
| Drizzle 替换 Prisma | ❌ | Prisma 已满足需求，迁移成本大于收益 | 需要跨进程共享 schema 工具链 |
| TanStack Router / Table / React Hook Form | ❌ 暂不采用 | AntD 的 Table/Form 已够用；换掉等于重写全部页面 | 需要虚拟表格或类型安全路由成为瓶颈 |
| Biome 替换 ESLint + Prettier | ⬜ 待定 | 收益明确，但一次性重排格式会污染 diff | 单独开一个纯格式提交 |
| Turborepo 替换 npm scripts | ❌ | 单人项目，`scripts/build.mjs` 已足够 | 需要并行任务缓存 |
| FSD / 六边形整体重构 | ❌ | 分层已成立；问题在「金额语义没唯一实现」，已由领域层解决 | — |
| 游标分页 | ❌ | 见决策 #16 | 见决策 #16 |
| i18n 框架 | ❌ 现在不做 | 单语言时框架是纯负担；但**文案目录从今天开始建**（见决策 #30） | 出现第二种语言需求 |
| **Git 提交做实时同步** | ❌ 不做协议，只做介质 | Git 的分支/合并语义与记账合并语义不匹配；但作为「加密容器搬运 + 免费版本历史」的介质是划算的（见决策 #31） | — |
| **CRDT / 协同编辑引擎** | ❌ | 单用户 2–4 台设备，冲突率极低；CRDT 的复杂度远超收益 | 出现真正的多人同时编辑同一本账 |
| **增量变更日志（op log）作为 v1 方案** | ❌ 推迟到 S2 | 快照语义已足够且更简单；op log 要处理 seq 连续性、半写文件、与业务写的同事务落库，复杂度高一档 | 单容器 >50MB 或账本 >10 万条 |
| **自建同步服务器** | ❌ | 需要账号体系、运维、带宽与可用性；违背「数据在用户手上、没有服务存活依赖」的产品承诺 | 用户明确要求多端实时协作 |
| **厂商 API 直连（Drive / Dropbox）做主同步通道** | ❌ 暂不做 | 每家一套 OAuth、配额与审核；先用本地目录与 WebDAV 覆盖绝大多数场景 | 目录与 WebDAV 在目标设备不可行 |
| **React Native / 全原生重写移动端** | ❌ | 现有 React + Vite 构建产物可复用；WebView 顶不住时按屏幕引入原生页，而非整体重写 | V2/V3 真机实测显示整体方案顶不住 |

## 附：一句话验收

> 新成员只看 `packages/domain/src/ledger` 就能说出「退款和转账手续费怎么算」，
> 并且能在 10 分钟内加一种新交易类型而不用改报表——
> 同时，数据能迁移、能备份、能恢复、能撤销，数字对不上时系统会自己说出来。
> 这时架构才算成立。
