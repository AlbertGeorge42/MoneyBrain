## 1. 产品终局

**一句话**：一个自己掌控数据的钱包式个人财务工具——数据以加密文件的形式躺在你自己的网盘 / NAS 上，手机和电脑都能记账、都能看数，两端最终一致，没有账号、没有服务器、没有云厂商。

```
        ┌──────────────── 用户自己的设备 ────────────────┐
        │  PC（主）                      手机（副）        │
        │  记账 · 报表 · 预算 · 投资     记账 · 速览 · 拍照 │
        │       ↕                          ↕              │
        │        加密账本文件（自己选网盘 / NAS）          │
        └─────────────────────────────────────────────────┘
                    数据在用户手上，钥匙也在用户手上
```

四条产品承诺（决定架构取舍时以此为准）：

| # | 承诺 | 含义 | 对架构的强制要求 |
|---|---|---|---|
| 1 | **数据在用户手上** | 任何时候能用标准工具读出全量账目，不被任何服务锁定 | 导出格式长期稳定；加密容器格式公开可解 |
| 2 | **密钥在用户手上** | 恢复码由系统生成（≥128 位熵），用户抄写保管，**不由用户自选**（自选口令无法保证熵，见 [stage-2](blueprint/stage-2-sync.md)）；换设备只靠恢复码，不需要任何人找回 | 恢复码必须能独立恢复全部数据；无后门；泄露后可更换（重加密全部容器） |
| 3 | **两端数字一致** | 手机记的账，电脑上立刻看得到；反之亦然 | 同步必须可重放验证（不变量 7） |
| 4 | **不依赖服务存活** | 厂商倒闭、账号被封、网盘限流，都不影响本地记账 | 离线优先；同步是后台增强，失败可见但绝不阻塞 |

**终局形态的完整清单**，以及它落在哪：

| 能力 | 落在哪 |

## 2. 优先级规则

**质量优先级（冲突时按此排序）**：

```
数据不丢 > 数字可信 > 可解释 > 结构清晰 > 交互顺手 > 好看
```

只有当前一层的任务全部收口，才开始下一层。

**产品优先级（决定做什么顺序）**：

```
地基可信  →  界面可用  →  同步契约  →  跨设备可用  →  自动同步  →  自动记账  →  第二语言
```

- **地基先于界面**：口径对不上、数据会丢、service 越写越烂，这些不修，
  后面每加一个功能都建在流沙上。
- **界面先于新功能**：界面债的特点是**越往后越贵**。拖到移动端做完再统一，
  等于两个端各改一遍；而新功能可以按需再加，加了还得在统一的地基上写。
- **i18n 基础设施与界面一起做**：抽取成本随代码量线性上升，阶段 1 正好要逐个改组件，
  顺手抽进目录只多一次改动。**但第二种语言仍然最后**——框架接入是纯负担，
  只在真的有第二种语言时才做。
- **同步契约先于移动端**：手机端从第一天就按同一套契约写，否则会先写出一套
  不兼容的数据，等于两端各改一遍。
- **同步先于自动记账**：自动记账产生的数据也必须能被同步，否则手机上自动记的账在电脑上是空的。

**产品优先级不等于实现顺序**：产品上「手机能用」排在「同步」前，实现上「同步契约」排在「手机」前（见 §3）。

**提交粒度**：一次提交做**一件事**——一个功能或一次口径改造，它带来的连带代码精简
（删旧实现、删死代码、删冗余依赖、合并重复实现）属于同一件事，在同一次提交里完成。
只有当「精简」本身与本次改造无关时，才值得单独开一次提交。

## 3. 开发路线

```
阶段 0 · M0 单机可信 ──> M1 结构收口          ← 现在在这
阶段 1 · M2 体验与桌面化
阶段 2 · M3 同步地基 ──> M4 跨设备可用 ──> M5 自动同步
阶段 3 · M6 通知自动记账
阶段 4 · M7 延后与按需扩展
```

| 里程碑 | 优先级 | 内容 | 用户看到什么 | 出口条件 | 阶段文档 |
|---|---|---|---|---|---|
| **M0 · 单机可信** | P0 | B1–B3、C1–C3、A0、A3 | 记账不再怕误删与覆盖导入；报表期间统一 | 覆盖导入可回退；删除可撤销；报表期间统一；不变量 1–6 在随机序列上恒成立 | [stage-0](blueprint/stage-0-foundation.md) |
| **M1 · 结构收口** | P0 | D1–D7、D9 | （无用户可见变化，是给后面铺路） | service 不碰 Prisma；并发写无冲突；列表与报表查询量只随期间增长（余额是 O(历史) 的明确例外，见 D7）；repository 成为移动端可替换的缝 | [stage-0](blueprint/stage-0-foundation.md) |
| **M2 · 体验与桌面化** | P0 | U0–U12、E1–E4、E6、L1–L3、K8 | 界面统一可信、键盘可走通主流程、加载/空/错三态一致、装得上双击即用、文案可查表 | 「PC 端可用」清单全部达成（见 [stage-1](blueprint/stage-1-experience.md)） | [stage-1](blueprint/stage-1-experience.md) |
| **M3 · 同步地基** | P1（PC） | F1–F11 | 账本能导出成一个加密文件 | 加密容器可导出可导入；版本向量合并任意顺序结果一致；备份与同步共用一套加密；容器格式可独立解密 | [stage-2](blueprint/stage-2-sync.md) |
| **M4 · 跨设备可用** | P1 | H1–H8 + G1、G6、G7、E5 | 手机能装；账能用文件在设备间搬 | 手机与桌面导出的容器互相可读；新设备 10 分钟恢复出同样余额 | [stage-3](blueprint/stage-3-mobile.md) |
| **M5 · 自动同步** | P1 | G2–G5、G8 | 两端自动收敛，不用手动搬 | 网盘 / NAS / GitHub 任一介质都能同步；冲突可见且不重复计钱；恢复码可更换 | [stage-2](blueprint/stage-2-sync.md) |
| **M6 · 通知自动记账** | P2 | I1–I6 | 手机自动识别消费通知 | 真机候选可解析、可确认、可去重；失败可见；原文不出设备 | [stage-3](blueprint/stage-3-mobile.md) |
| **M7 · 延后与按需扩展** | P3 | K1–K7、J1–J4 | 周期交易、标签、多账本等推迟的功能；或按触发条件开工的条目 | 每条独立验收 | [stage-4](blueprint/stage-4-expansion.md) |

**关键依赖**（错了两端都要返工）：

- **F → H**：手机端必须从第一天就按同一套同步契约写。
- **F 与实体集合解耦**（批次 F11）：周期交易、标签、多账本（阶段 4 的 K1–K3）决定可同步实体
  的集合。它们的落地被推迟，**所以容器格式不能与实体集合耦合**——记录自带 `entityType`，
  合并算法不认识具体实体类型。这样 K 批次落地时是增量工作，不会让两端一起返工。

**为什么 M3 在 M4 之前，却不是「先做同步」**：M3 只做数据契约与加密容器，没有网盘、没有第二台设备，
所以它仍属于 PC 阶段；它让移动端从第一天就按同一契约写，避免 M4 之后返工。

## 4. 设计不变量

任何实现都必须满足这 12 条，且每条都要有自动化测试。
测试覆盖情况见 [testing.md](testing.md) §5.1（那里是覆盖状态的唯一来源）。

**1–6 条是记账内核的不变量**，从 M0 起生效，任何阶段都不得破坏；
**7–11 条是数据安全与同步的不变量**，在对应批次落地时开始生效（见表内「生效于」——
在此之前不提前实现，也不视为违规：例如 F5 之前备份是明文 ZIP 属过渡态）；
**12 条是界面诚实性不变量**：「失败不显示 0 / 空列表 / 错误位置」从 M0 起生效且已有测试；
「焦点可见」与「三态一致」两部分随 M2 的批次 U（U7/U8）生效——在那之前不视为违规。
界面侧验收见 [stage-1](blueprint/stage-1-experience.md) 批次 U。

| # | 不变量 | 生效于 |
|---|---|---|
| 1 | 对账恒等式：`期末净资产 − 期初净资产 == 净收入 − 净支出 + 其他`（同期间、同口径）。`其他 = 不计收支净额 + 转账手续费 + 平账净额 − 期初前流水`，与 `db:verify` 与收支表对账条的口径完全一致 | M0 |
| 2 | `Σ 所有账户余额 == 净资产` | M0 |
| 3 | 任意交易：`Σ 分录.amount == 0`（复式平衡） | M0 |
| 4 | 退款：`退款后余额 == 原交易前余额`（全额退款时），且退款额 ≤ 可退余额 | M0 |
| 5 | 转账：`Δ转出 + Δ转入 == −fee` | M0 |
| 6 | 同一笔交易在余额、收支表、现金流量表、预算、投资分析中的「归属」可追溯到同一组分录 | M0 |
| 7 | 同步可重放：把全部设备的变更按确定性顺序应用到空库，得到与任一设备逐笔一致的状态（余额、报表、可退额） | M3 · F4 |
| 8 | 冲突不静默：同一实体只应用一个版本，另一版本必须留存且可见；绝不把两个版本都当交易入账 | M3 · F4 / G4 |
| 9 | 密文出端：同步文件与备份文件中没有明文账务数据，密钥/口令/恢复码不进入任何上传文件 | M3 · F5 |
| 10 | **合并与传输解耦**：同一组变更无论经由目录 / WebDAV / GitHub 哪种介质、以何种到达顺序应用，最终状态相同。合并在**记录层**做，不在文件层做 | M3 · F4 |
| 11 | **加密不降级**：账本文件（含备份、快照、同步文件）一律是密文；明文只存在于设备本地的 SQLite | M3 · F5（F5 前明文 ZIP 备份为过渡态） |
| 12 | **界面不骗人**：任何展示的数字与状态必须来自真实数据；失败显示原因而不是退化成 0、空列表或错误的位置（M0）；键盘可聚焦的元素焦点必须可见、加载/空/错三态一致（M2 · U7/U8） | M0（失败呈现）· M2（焦点可见、三态一致） |

## 5. 一句话验收

> 新成员只看 `packages/domain/src/ledger` 就能说出「退款和转账手续费怎么算」，
> 并且能在 10 分钟内加一种新交易类型而不用改报表——
> 同时，数据能迁移、能备份、能恢复、能撤销，数字对不上时系统会自己说出来。
> 这时架构才算成立。
