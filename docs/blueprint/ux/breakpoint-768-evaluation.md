## 1. 结论先行

推荐**方案 1：768–1023 侧栏收窄为 64px 图标轨（CSS 实现）**。

- 内容可用宽从 476–731 提升到 648–903，768 处的悬崖从 −239px 缩到 0（同一布局内连续），时间条在 768 恢复单行（h88 → h44）。
- 不动断点、不动 `device` 判定、不碰任何页面页头，820 栅格规则保留。
- 代价：768 报表页头仍然换行（648 < 实测阈值 686），图标轨牺牲导航可发现性，侧栏「本月收支」页脚在 768–1023 不可见，1024 处出现一次 −171px 的模式切换台阶。

如果「768 页头必须单行」是硬指标，方案 1 单独做不到（需再从 tab 区省 38px），此时才升级到方案 2。

**结论：按实测，三个「挤压症状」里有两个已经不成立。**

- 预算标题：已由时间器迁移修好，476 起就是单行。
- 时间条换行：768 的 h88 是「放不下就换行」的设计行为，不是溢出或截断；476 下没有横向溢出（`scrollWidth == innerWidth`）。
- 页头换行：确实是 768–900 的现状，但 476 宽下要单行，页头总需求 686，唯一可行做法是隐藏副标题（省 261.5）或把 tab 区从 327 压到 ~66，前者已被否决，后者等于重做视图切换。

因此方案 4 真正剩下的只有「476 本身偏窄」：报表表格、卡片、图表都只能单列，需要更多纵向滚动。这个问题靠局部 CSS 修不掉。

**改动面**：0–30 行（若坚持压缩页头/时间条）。**破坏面**：无。最坏情况：症状被管理而非解决，768–900 长期保持低信息密度。

## 7. 推荐与最坏情况

**推荐方案 1（64px 图标轨）**，理由按权重排序：

1. 内容宽提升最直接：768 从 476 → 648（+36%），1023 到 903；同一方案覆盖全部区间，无新断点。
2. 破坏面最小：不碰 `device` 判定、不碰页头、不碰 `ControlRow` 的 768 换行规则；820 栅格规则原样保留，只需重截基线。
3. 时间条在 768 从两行回到单行，正是这轮时间器统一的延续。
4. 纯 CSS 可落地，后续要加「悬停展开」时再引入浮层，不必一次做完。

**最坏情况（必须接受这四点才选它）**

- **768 报表页头仍然换行**：648 < 实测阈值 686。方案 1 只解决内容宽度和时间条，不解决页头单行。若要单行，需再从 tab 区省 38px（降低 tab 内距/间距），这属于第二小步，仍不涉及断点。
- **导航可发现性下降**：768–1023 只剩图标，文字、快捷键提示、品牌名、侧栏「本月收支」都不可见；「记一笔」按钮是 portal，宽度算式依赖 `--mb-sidebar-w`，不改会溢出。无障碍上文字仍在 DOM 里（视觉隐藏），但新用户识别成本上升。
- **侧栏页脚吸底（已验收）在这段区间失效**：这是对已验收成果的明确让步，需要你确认可以接受。
- **1024 处新增一次 −171px 的模式切换**（903 → 732）。建议把它当作「展开侧栏」的主动过渡处理，而不是当作布局断裂。

**备选触发条件**：如果「768 页头单行」被列为硬指标，或「本月收支」必须常驻，则改选方案 2；它能到 712 并让页头单行，但要把导航入口接进 5 个页头或 shell 层，回归面明显更大。方案 3 不建议：它把 820 已验收栅格作废，却只把 239px 的悬崖挪到另一个宽度。
