# Excel → MoneyBrain 数据模型对齐与重建方案

> 目标：让 app 能**替代** `2026财务管理.xlsx`。
> 本文只读分析，未删除、未写入任何数据库数据，也未修改代码。
> 数据源：`c:\Users\George\Documents\Life\Money\2026财务管理.xlsx`、同目录相邻文件、`.artifacts/qianji-import-2026-11-06/` 的钱迹 CSV 与 `package/mapping.json`。
> 金额单位：元，保留 2 位小数；app 内部为分（BigInt）。负债在 Excel 中以正数表示欠款，在 app 账户余额中以负数表示。

## 0. 结论摘要

- **Excel 是「月度汇总表」，不是流水账**：26 张 sheet 中没有交易明细表，每月只有资产负债表 + 上月收支汇总 + 2026 年新增的现金流水表。历史流水只能来自钱迹 CSV，这一点与用户第 2 条决定一致。
- **时间语义**：`2025-01`…`2026-11` 每张月度 sheet 的资产负债表是**该月月初余额**，收支表是**上月流水**。例如 `2026-02` sheet 的 H4 引用 `2026-01!E23`，余额是 2026-02-01 的余额。全表共 **23 个月初锚点**。
- **账户**：Excel 15 个账户行（9 资产 + 6 负债）；钱迹 12 个账户与其中 12 个 **1:1 对上**，没有 CSV 独有账户。Excel 独有的 `未报账项`（仅 2025-10 为 184.12）、`个人借款`（恒 0）、`个人欠款`（恒 0）。
- **净资产**：2025-01-01 为 **339,848.61**；2026-11-01 为 **1,115,552.48**（总资产 1,116,868.88，总负债 1,316.40）。
- **分类**：原始 **14 个一级 + 40 个二级**；落到 app 需按收入/支出拆开，变成 **15 个一级 + 41 个二级**（`投资/基金` 在支出侧另立 `投资亏损/基金`）。
- **期初结转**：Excel 不靠流水推导，而是**每月手填月初余额**；收支表的期初资产引用上月净资产，平账行是「真实期末 − 理论期末」。因此 app 必须复刻「月初锚点 + 差额吸收」，不能只取一个 2025-01-01 期初硬推 21 个月。
- **账户级残差**：用「Excel 月初锚点 + 钱迹流水」逐月推导，共 **90 条非零差额**（绝对值合计 34,528.97，净额 +5,187.33）。其中 12 个钱迹账户 **2025-04 起仅 70 条、绝对值合计 287.86**；另有 Excel 独有的 `未报账项` 2 条（2025-09 +184.12、2025-10 −184.12，一次性应收挂账）。2025-01～03 的大额是初始化/时点差异（雪球 +10,181.14、银行卡 −9,778.56、白条 ±4,169 两条对冲）。
- **2026 年逐月验证**：10 个月末的「Excel / 锚点+流水推导 / 差额」全部在 **±19.20 元**内；补 90 条平帐记录后逐月归零。
- **后端现状**：`Transaction(type='adjustment')` 已能承载平帐（进流水、可筛选、可撤销、不计收支/预算），但**没有「账户+日期+真实余额」的一键接口**；且编辑账户「当前余额」会把差额折算进 `initialBalance`，与平帐冲突。
- **重建结论**：清库后建 13 个账户（12 个钱迹账户 + `未报账项`）、15/41 个分类、导入 3,291 行 CSV、补 90 条历史平帐记录；`initialBalanceDate = 2024-12-31`。不需要 schema 迁移。

### 1.2 月度 sheet 的三块区域

**A. 资产负债表**
- 2025 版：`B4:E21`；2026 版：`B4:E23`（新增 `现金` 行，总额/净资产下移 2 行）。
- 资产区：`流动资产`（支付宝余额、微信余额、银行卡、现金、公积金）→ `金融资产`（雪球基金、支付宝基金）→ `应收账款`（未报账项、个人借款）。
- 负债区：信用卡、花呗、白条、美团月付、1688、个人欠款。
- 每个区块带 `总计` 与 `占比`；末尾 `总资产`、`总负债`、`净资产`、`负债率`。
- 数据行是**手填数字或内联算式**（如 2025-12 `C7 = 8571.9+86458.22`）；只有总计/占比/净资产是公式。

**B. 收支记录表**
- `G4:H37`，2025/2026 同构（2026 增加 `优惠券` 收入行）。
- 收入：工资、红包、转账、公积金、其他、优惠券 → `现金收入`；雪球基金、支付宝基金、余额宝、微信零钱通、银行理财 → `投资收入`；`总收入`。
- 支出：餐饮、服饰、交通、生活、恋爱、消费、娱乐、送礼、其他 → `总支出`。
- 底部：`结余`、`储蓄率`、`理论期末资产`、`平账`、`真实期末资产`。
- 所有行都是**月度汇总数**，没有交易级明细；多数格子是手填，少数是内联算式（如 `H6 = 129810+24345.95`、`H15 = -676.56-6.3`、`H14 = 6939.72+11600.77-908.34`）。

**C. 现金流水表（仅 2026 版，J4:K20）**

| 行 | 内容 | 典型公式/值 |
|---|---|---|
| J4/K4 | 期初现金 | `=SUM('2026-01'!C6:C9)`（跨表引用，范围有时含现金、有时不含） |
| J6/K6 | 生活变动·收入 | `=H6+H7+H8+6276`（公积金 6,276 **硬编码**，未引用 H9） |
| J7/K7 | 生活变动·消费 | `=1279.23+146.82`（**硬编码**逐项相加） |
| J10/K10 | 投资变动·收益 | `=H16+H17+H18` |
| J11/K11 | 投资变动·投资 | `31000`（**硬编码**当月投资支出） |
| J15/K15 | 筹资变动·还款 | `=8660.31+1151.19`（**硬编码**逐笔相加） |
| J18/K18 | 理论期末现金 | `=K4+K17` |
| J19/K19 | 平账 | `=K20-K18` |
| J20/K20 | 真实期末现金 | `=SUM(C6:C8)`（2026-02）或 `=SUM(C6:C9)`（2026-01/06/11），**范围不一致** |

结论：这张现金流表是**手工拼装的对账表**，不是从收支表自动生成的报表；跨表引用 + 硬编码混合，是 Excel 最脆弱的部分。

### 1.3 关键公式原文

资产负债表（2025 版行号；2026 版整体下移）：

```
C7  = 8571.9+86458.22          '银行卡 = 两个子账户余额相加（手填算式）
C9  = SUM(C5:C8)               '流动资产总计
C10 = C9/$C$21                 '流动资产占比
C14 = SUM(C12:C13)             '金融资产总计
C19 = SUM(C17:C18)             '应收账款总计
C21 = SUM(C5:C8,C12:C13,C17:C18)  '总资产
E19 = SUM(E4:E9)               '总负债
E20 = E19/$C$21                '负债率
E21 = C21-E19                  '净资产
```

收支表：

```
H4  = '2025-12'!E21            '2026-01 的期初资产 = 上月净资产
H4  = '2026-01'!E23            '2026-02 的期初资产 = 上月净资产
H12 = SUM(H6:H11)              '现金收入（含优惠券）
H19 = SUM(H14:H18)             '投资收入
H21 = H12+H19                  '总收入
H32 = SUM(H23:H31)             '总支出
H33 = H21-H32                  '结余
H34 = H33/H21                  '储蓄率
H35 = H4+H33                   '理论期末资产
H36 = H37-H35                  '平账 = 真实期末 − 理论期末
H37 = E23                      '真实期末资产 = 当月资产负债表净资产
```

### 1.4 手填 vs 公式（判定）

- **手填/内联算式**：所有账户余额（C/E 列）、所有收支明细行（H6:H11、H14:H18、H23:H31）。
- **公式**：总计、占比、负债率、净资产、现金收入/投资收入/总收入、总支出、结余、储蓄率、理论期末、平账、真实期末。
- **跨表公式**：每月 H4 引用上月的净资产；现金流水 K4 引用上月的现金账户。
- 因此 Excel 的「报表」是**汇总层**，账户余额是**人工锚点**，不是流水推导结果。

## 2. 账户体系

### 2.1 Excel 的账户表达

Excel 没有独立的「账户表」：账户 = 资产负债表中的一个行标签，类型由所在区块决定（资产/负债），没有币种、期初日期、是否计入净资产等字段。隐含规则：

- 资产余额填正数，负债余额也填正数（表示欠款）；
- 所有 15 行都计入总资产/总负债，没有「排除某账户」的开关；
- 月初余额每月手填，没有「期初余额 + 流水」的字段；
- 银行卡行可以是两个子余额的内联算式（如 `=12737.42+78587.81`），app 侧应合并为一个账户。

### 2.3 账户对照结论

- **CSV 有、Excel 没有**：无。12 个钱迹账户全部 1:1 对上。
- **Excel 有、CSV 没有**：3 个。`未报账项`（仅 2025-10 为 184.12，其余 0）、`个人借款`（恒 0）、`个人欠款`（恒 0）。
- **名称不同但同一账户的确认依据**：
  - `民生银行` = `信用卡`：527 行全部是支出/还款，没有收入；按信用卡余额口径对账，2025-04 起残差稳定在 +6.00/月（分期/尾差），与信用卡欠款一致。
  - `云闪付` = `银行卡`：764 行覆盖工资入账、日常消费、转账；Excel `C8` 是两个子余额相加（2026-11 `=12737.42+78587.81`），金额与 CSV 月度余额一致。
  - `京东白条` = `白条`：44 行，2025-2026 锚点可对上；2025-02/03 有 ±4,169 的时点差（见 §4.4）。
  - `微信` = `微信余额`、`支付宝` = `支付宝余额`：名称近似且月度锚点残差 ≤ ¥10。
- **结论**：不需要为「CSV 有、Excel 无」建账户；`未报账项` 建一个 0 期初的应收账户，承载 2 条平帐（2025-09 +184.12、2025-10 −184.12）。跳过它会把 184.12 并进其他账户的平帐，破坏账户级可解释性，不推荐。

## 4. 期初、结转与平账机制

### 4.1 sheet 的时间语义（最关键）

- `2025-01` sheet 只有资产负债表，没有收支表 → 它是 **2025-01-01 的锚点**。
- `2025-02` sheet 的 H4 `='2025-01'!E21'` → 收支表期初 = 2025-01-01 净资产；H37 `=E21` → 真实期末 = 2025-02-01 净资产。也就是说，`2025-02` sheet 的收支是 **2025 年 1 月的流水**，余额是 **2025-02-01 的余额**。
- 同理，`2026-01` sheet 的收支是 2025-12 的流水，余额是 2026-01-01 的余额。
- 所以：**sheet 标签 = 月初锚点；收支表 = 上一个自然月。**

这验证了用户第 3 条中「月初真实余额」的做法，也决定了 app 的期初日期。

### 4.2 期初从哪来

- 没有「上月结转」公式：账户余额是**每月手填**（或内联算式），不是上月余额 + 流水。
- 只有净资产/总资产的合计是公式。
- 收支表的 `期初资产` 引用上月净资产，仅用于计算 `理论期末资产` 与 `平账`，不反过来写回账户余额。

### 4.3 平账行

- `H36 = H37 - H35`，即 `真实期末资产 − (期初资产 + 结余)`。
- 2025-02 起多数月份的 H36 是**个位数到几十元**；2025-03 为 **−427.10**；2026 年多为 ±几十元。
- 但 H36 是 **P&L 口径**的平账，不是账户级残差。两者不同的原因：Excel 把优惠券、转账、投资收入按产品手工归集，且现金流水表是手拼的；账户级残差只看「真实余额 vs 流水」。
- 用户实际操作是**改写月初余额**（C/E 列），不是录入 H36；H36 只是结果展示。

### 4.4 账户级残差（本方案用于生成平帐记录）

用「Excel 下月月初锚点 − (本月锚点 + 钱迹本月流水)」逐账户计算：

- 全部历史 **90 条**非零差额（|差额| ≥ 0.005），绝对值合计 **34,528.97**，app 有符号净额 **+5,187.33**。
- 12 个钱迹账户：**2025-04 起 70 条**，绝对值合计 **287.86**，净额 **+215.32**——这才是「个位数/几十元级」的常态。
- `未报账项`：**2 条**，2025-09-30 +184.12、2025-10-31 −184.12（Excel 里 2025-10 月初挂账 184.12，11 月归零），一次性应收，不属于月度误差。
- 2025-01～03 的大额是初始化/时点差异：
  - 2025-01 雪球基金 **+10,181.14**、银行卡 **−9,778.56**（两笔近似对冲，净 +402.58）；
  - 2025-02 白条 **+4,169.00**、2025-03 白条 **−4,169.00**（两笔对冲，来自白条消费与还款的时点差异）；
  - 2025-03 银行卡 +4,175.99、白条 −4,169.00。
- 因此不能只取 2025-01-01 一个期初硬推：累计会漂移 **+5,187.33**；到 2026-10 的净额仍然如此。必须用月度锚点 + 平帐记录。

### 4.5 对 app 的含义

1. **期初**：取 2025-01-01 全账户余额；`initialBalanceDate = 2024-12-31`（因为 `balanceAt` 的期初是「期初日期当天开始前」，若设 2025-01-01 会漏掉 1 月 1 日当天流水）。
2. **月度锚点**：不落成 23×15 的独立锚点表；用「锚点日输入真实余额 → 自动生成一条 adjustment」实现，等价于用户现在改写月初余额。
3. **差额吸收**：每条平帐记录日期 = 该流水月的最后一天（这样下月 1 日的 `balanceAt` 能包含它）。
4. **历史平帐**：90 条，见 §8.7。

## 5. 实际在用的报表与分析

### 5.1 资产负债表

- 结构：流动资产 / 金融资产 / 应收账款 / 流动负债；每块有总计与占比。
- 口径：`净资产 = 总资产 − 总负债`；所有 15 个账户都计入，没有排除项。
- app 对应：`balance-sheet.service.ts` 已按 `Account.type` 汇总；账户分组用 `AccountCategory`。**可直接承载**，但「占比/负债率」需要在报表层补（当前净资产/资产构成有，负债率未确认）。

### 5.2 收支表

- 收入分两类：现金收入（工资/红包/转账/公积金/其他/优惠券）+ 投资收入（5 个产品）。
- 支出 9 类（餐饮/服饰/交通/生活/恋爱/消费/娱乐/送礼/其他）。
- `储蓄率 = 结余 / 总收入`；`结余 = 总收入 − 总支出`。
- **口径差异**：
  - Excel 把 `优惠券` 计入现金收入；app 只展示、不计收入。
  - Excel 把 `转账`（H8）计入收入（2025-02 1,962.21、2025-03 5,000、2025-08 300）；app 的 transfer 类型不计收入。
  - Excel 的 `投资收入` 按产品分 5 行；app 只有「投资/利息」「投资/基金」两个分类 + 账户维度，产品维度用账户近似（余额宝/零钱通/银行理财在 CSV 中并入支付宝/微信/云闪付，无法再分产品）。
  - Excel 的投资亏损用「投资/基金 + 支出」15 行表达；app 需单列「投资亏损」分类，报表用「投资损益净额」展示。
- app 对应：`income-expense.service.ts`。**可直接承载**，但需补上述口径说明与「投资损益净额」。

### 5.3 现金流量表（Excel 的手工对账表）

- 结构：期初现金 → 生活变动（收入/消费）→ 投资变动（收益/投资）→ 筹资变动（借贷/还款）→ 净变动 → 理论期末现金 → 平账 → 真实期末现金。
- 现金范围：支付宝/微信/银行卡/现金，**不含公积金与基金**。
- 但实现是手拼的（硬编码公积金 +6,276、投资 31,000/30,000/46,000、还款逐笔相加；K20 范围在 `C6:C8`/`C6:C9` 间不一致）。
- app 对应：`cash-flow.service.ts` 已按 `isCashEquivalent` 自动取现金账户，期初/期末用余额口径，结构上优于 Excel。**差距**：没有「平账」行，导致 `期初 + 净流量 ≠ 期末`（见 §8.5）。

### 5.4 年度汇总与一次性支出

- `2025汇总`：12 个月横向汇总；年度 `总收入 611,524.18`、`总支出 188,351.82`、`结余 423,172.36`、`平账 −250.88`。
- `2026汇总`（1–10 月）：`总收入 419,280.21`、`总支出 66,536.57`、`结余 352,743.64`、`平账 +38.75`。
- 2025 汇总公式**手工剔除**两笔一次性大额：`68,888.00`（2025-02 其他）与 `48,722.25`（2025-07 其他，原值 48,802.26，差 80.01）。
- app 现状：没有「一次性/非经常」标签或剔除规则；年度汇总只能用分类/标签近似。**需扩展**。

### 5.5 投资记录（三分法）

- `2026投资记录.xlsx` 月度 sheet：类别（债券/股票/商品）、资产、投入、收益、收益率、实际占比、目标占比、偏差值、修正金额（比例 100%）；另有「有知有行」账户；`定投金额 1000`、`修正天数 4`。
- app 对应：`InvestmentAssetClass(targetRatio)` + `InvestmentAllocationSnapshot(accountBalance)` + `InvestmentAllocationItem(marketValue, periodNetFlow)`。
- **可直接承载**的：类别、目标占比、市值、期间净流入、实际占比、偏差。
- **需扩展**的：`投入`（累计成本）、`收益率`、`修正金额`、`修正天数`、`定投金额`——模型里没有这些字段，需要报表计算或新增字段。
- **无法从 CSV 生成**：CSV 只有基金账户的收入/支出，没有持仓市值与资产类别；三分法快照必须手工录入（与用户现有 Excel 月度记录同频）。

### 5.6 FIRE / 回测

`fire_proj/retire_money.py` 是独立 FIRE 测算；`invest_compute`、`export_invest`、`invest_backtest` 是基金计算/导出/回测脚本。均不在 app 数据模型内，本轮不纳入重建。

## 6. 与当前 app 模型的差距

### 6.1 能直接承载的

- 账户名称/类型/排序/图标/颜色：`Account.name/type/sort/icon/color`。
- 期初余额/期初日期：`Account.initialBalance/initialBalanceDate`。
- 账户分组 + 现金等价/投资标识：`AccountCategory.type/isCashEquivalent/isInvestment`。
- 收支分类两级：`TransactionCategory.parentId`。
- 交易（收入/支出/转账/退款/平帐）与不计收支：`Transaction.type/excludeFromIncomeExpense`。
- 退款关联：`relatedTransactionId`。
- 平帐与撤销：`Transaction(type='adjustment')` + `AuditEvent`。
- 净资产/资产负债：`balance-sheet.service.ts`。
- 收支表：`income-expense.service.ts`。
- 现金流：`cash-flow.service.ts`（按现金等价账户自动计算）。
- 投资配置：`InvestmentAssetClass` / `InvestmentAllocationSnapshot` / `InvestmentAllocationItem`。

### 6.2 三个最大差距

1. **对账不是一等公民**：没有「账户 + 锚点日 + 真实余额 → 自动生成平帐记录」的一键入口；用户仍要在交易表单里手算差额、手动选 adjustment。且编辑账户「当前余额」会把差额折算进 `initialBalance`（`LedgerContext.tsx` 441–446），与平帐机制冲突。
2. **报表口径有缺口**：现金流量表没有「平账」行，`期初 + 净流量 ≠ 期末`；流水页 `summarizeTransactions` 把 adjustment 计入收入/支出合计（`features/transactions/filters.ts`）；Excel 的手工现金流表无法用 app 现有报表一比一复现。
3. **分析与投资维度不足**：Excel 的年度一次性支出剔除、资产增速、现金占比、投资三分法的投入/收益/收益率/修正金额/定投参数，没有对应报表或字段；投资快照只能手工维护，CSV 不能提供市值与资产类别。

其他差距：多币种（无字段，但全 CNY 无损）、标签/项目（CSV 全空，当前不需要）、`是否计入净资产` 开关（无，但全账户计入与 Excel 等价）、`优惠券` 是否计收入（口径不同，需按 CSV 规则）。

## 8. 对账与锚点（专节）

### 8.1 Excel 的平帐取证

- **没有隐藏的对账 sheet**：26 张 sheet 全部是月度表/汇总表；没有「调整」「对账」「差异」命名的 sheet。
- **没有逐账户的调整行**：资产负债表只有账户余额行，没有「调整」行；P&L 的 `平账`（H36）是**公式输出**，不是可追溯的记录。
- **实际做法是改写月初余额**：每月在 C/E 列直接填真实余额；`H36 = H37 - H35` 只是展示差额。
- **现金流水表也有平账行**：`K19 = K20 - K18`（2026 版），同样是公式输出，且整张表是手工拼的（§1.2）。
- **结论**：Excel 的平帐**不留痕**，只保留结果。app 要做的是把「用户输入真实余额 → 差额」变成**可见、可筛选、可撤销的记录**，同时保持输入省事。

### 8.2 后端现状核实（逐项）

| 问题 | 结论 | 代码位置 |

| 流水页合计是否含平帐 | **含**（会虚增收入/支出） | `apps/web/src/features/transactions/filters.ts` 169–179 |

**与用户预期是否一致**：用户认为「后端现在应该已经支持」。**部分一致**：

- 一致：`adjustment` 实体、进流水、可筛选、可撤销、不计收支/预算、余额与净资产即时一致——这些都已有。
- 不一致：**没有一键校准接口/入口**；差额修正仍靠用户手工建 adjustment；账户「当前余额」编辑走的是 `initialBalance` 折算，不是平帐记录；现金流报表缺平账行；流水页合计误把平帐计入收支。

### 8.3 目标行为（按用户第 4 条）

1. 用户在界面填「账户 + 锚点日 + 真实余额 + 原因」。
2. app 计算 `balanceAt(锚点日)` 的账面推导值，差额 = 真实余额 − 推导值。
3. 预览：账户、锚点日、推导值、真实值、差额、将生成的平帐记录日期/金额。
4. 确认后**自动生成一条 `adjustment`**：
   - 金额 = 差额（负债账户按 app 有符号规则）；
   - 日期 = 锚点日的**前一天**（这样 `balanceAt(锚点日)` 能包含它）；
   - 无分类；`note` = 用户原因，默认「月度对账 YYYY-MM」；
   - 可选：把 `importBatchId` 写进 `note` 或 `ImportBatch.createdJson`。
5. 该记录进流水、可筛选「调整」、可撤销（审计事件）、参与余额/净资产。
6. 同账户同锚点日重复提交：
   - 先查是否已有 adjustment；有则提示「已存在 ¥X，是否覆盖/追加」；
   - 推荐**覆盖**（更新原记录，留审计），而不是静默追加。
7. 对账完成后，报表显示「本期对账差额」；现金流量表增加「平账」行。

### 8.4 平帐记录的口径决定

| 口径 | 决定 | 理由 |
|---|---|---|
| 是否计入收入/支出 | **不计入** | 平帐是余额修正，不是经济业务；计入会虚增收入/支出与储蓄率 |
| 是否影响预算用量 | **不影响** | 预算衡量消费，平帐不是消费；现有 rules 已天然排除 |
| 是否进流水列表 | **进**，类型「调整」，可筛选 | 用户要求可见、可追溯 |
| 是否进流水页合计 | **不进**（需修 `filters.ts` 169–179） | 现状会把 adjustment 计入收入/支出，必须改 |
| 是否进现金流量表 | **进「平账」行**，但不进生活/投资/筹资流量 | 否则 `期初 + 净流量 ≠ 期末`；这是当前报表的缺口 |
| 是否进净资产 | **进**（余额的一部分） | 平帐的目的就是让净资产等于真实值 |
| 撤销方式 | 软删除 + 审计事件 | 复用现有 `deleteTransaction` |
| 幂等 | 同账户同锚点日：查询 + 覆盖确认 | 避免重复记录；不需要 schema 唯一键 |

### 8.5 与 `initialBalance` 冲突的处理

现状有两条路径都能改变余额：

- A. 平帐：`adjustment` 交易（可见、留痕、可撤销）。
- B. 账户编辑：`LedgerContext.tsx` 441–446 把「当前余额」差额折算进 `initialBalance`（不可见、无流水、无审计）。

**建议二选一（推荐 A）**：

- 有流水后，**禁止**直接改 `initialBalance`；账户设置里「当前余额」字段改为「发起对账」按钮。
- `initialBalance` 只在「无流水 / 导入前」可编辑。
- 若保留 B，必须明确优先级：B 只用于初始化，之后一律 A；否则两条路径叠加会让余额无法解释。

### 8.6 数据模型结论：复用 vs 迁移

**结论：复用 `Transaction(type='adjustment')`，不新增表、不做 schema 迁移。**

理由：

- 已满足：金额、日期、账户、备注、进流水、可筛选、可撤销、参与余额/净资产、不计收支/预算。
- 缺的只是：一键入口（前端 + 一个薄服务）、现金流「平账」行（报表层）、流水页合计（前端）、重复检查（应用层）。
- 若未来「每月强制锚点」成为产品能力，可再加 `ReconciliationAnchor` 表（accountId + anchorDate + actualBalance + adjustmentId），但**当前不需要**。
- 影响范围：`balance-at` 不需要改（adjustment 已是普通交易）；净资产不需要改；预算不需要改；只需改现金流报表与前端入口。

### 8.9 强制每月锚点的利弊

- **利**：误差不累积（每月 ≤ 几十元）；能及时发现漏记/错记；与用户现有习惯一致；对账记录可见、可撤销。
- **弊**：每月多一步操作；如果用户为了「平掉」而输入真实余额，可能把真实的漏记交易隐藏进平帐记录（账面上看不出来）；90 条历史 + 每月 N 条会增加流水噪音。
- **建议**：**不强制**。做「本月未对账」提醒 + 一键对账入口；用户可以选择跳过，跳过时按流水推导，并在报表标注「未经对账」。历史 90 条作为一次性导入，不要求用户逐条确认。

## 10. 需用户决策（5 条）

1. **2025 年 1–3 月的大额初始化差额怎么处理？**
   - 方案 A（推荐）：保留为 3 条大额平帐（雪球 +10,181.14、银行卡 −9,778.56、白条 +4,169/−4,169），标注「历史初始化差额」。
   - 方案 B：把 2025-04-01 作为重建起点，丢弃 1–3 月流水，只保留 4 月后的 70 条小额平帐。
   - 影响：A 保留完整历史但前 3 个月流水噪音大；B 干净但丢失 2025 Q1。

2. **对账的日期口径用「月初余额」还是「月末余额」？**
   - 推荐：界面写「锚点日（月初）+ 真实余额」，内部把 adjustment 记在锚点日前一天；这与 Excel 的月初语义一致。
   - 若用户习惯说「月末余额」，则需要换算，容易差一天。

3. **有流水后，账户「当前余额」还允许直接改吗？**
   - 推荐：不允许；改余额 = 发起对账，生成 adjustment；`initialBalance` 只在导入前可编辑。
   - 备选：保留两条路径，但明确「initialBalance 只用于初始化」。

4. **是否强制每月锚点？**
   - 推荐：不强制；做「未对账」提醒 + 一键入口。
   - 若强制：需要新增 anchor 表/提醒机制，且用户每月必须操作一次。

5. **投资亏损（15 行「投资/基金 + 支出」）如何入账？**
   - 推荐：单列「投资亏损」支出分类，报表用「投资损益净额 = 投资收入 − 投资亏损」；不进日常消费预算。
   - 备选：并入「投资」收入分类用负数表达（需要模型支持负收入，改动更大）。
