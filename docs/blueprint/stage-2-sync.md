# 阶段 2 · 同步（M3–M5）

> **目标**：让两台设备上的账自动收敛，且**用户不失去对自己数据的控制**——
> 文件在自己的网盘/NAS 上，密钥自己拿着，没有账号、没有服务器、没有云厂商。
>
> 这一阶段的产物是手机端与桌面端的共同契约，因此**必须在移动端之前**。

## 本阶段要解决的问题

| # | 问题 | 归属 |
|---|---|---|
| 1 | ID 由服务端生成，离线创建的记录没有身份 | F1 |
| 2 | 交易没有修改版本与删除墓碑，无法判断"谁更新" | F2 |
| 3 | 没有账本与设备标识 | F3 |
| 4 | 没有合并算法，两端同时改会互相覆盖 | F4 |
| 5 | 备份是明文 ZIP，放网盘等于裸奔 | F5、F9 |
| 6 | 同步格式不公开，绑死后无法迁移 | F7、F10 |
| 7 | 没有传输通道 | G2 |
| 8 | 冲突无处安放 | G4 |
| 9 | 同步失败会被伪装成成功 | G3 |

## 同步架构

这一节是整个蓝图的架构核心。**先读懂它，再动手**——
同步的 bug 会直接表现为"两台设备数字不一样"，那是最伤信任的一类问题。

### 端拓扑

```text
桌面：apps/web → apps/api(HTTP) → app 用例 → Prisma/SQLite
手机：apps/mobile(Capacitor + React) → app 用例 → SQLite（手机本地）
共享：domain（算钱）· contracts（类型）· app（用例/仓储端口）· sync（加密/合并/应用）
同步：用户自己的网盘 / NAS / GitHub ↔ 加密账本容器 ↔ 每台设备的本地账本
```

- **桌面**：现有 React + Vite + Express + Prisma 全部保留，是第一客户端，也是规则验证场。
- **手机**：Capacitor + 现有 React 构建产物 + Kotlin 原生模块（通知监听、文件与密钥访问）。
  手机不跑 Express/Prisma，只实现 SQLite 仓储适配器。
  现有响应式布局先直接用；只有实测不达标时才针对屏幕引入移动控件，不整体换 UI 库。
- **iOS / iPad**：复用 UI、用例与领域层；通知自动记账**不承诺**。iPad 不是放大的手机，单独排期。
- 移动端复用现有 feature/query 层：把 `services/api.ts` 的实现换成「本地仓储适配器 + 相同的响应信封」，
  不为移动端重写一套数据流。手机数据量在 §3.9 包络内，报表直接调领域层纯函数，
  **不复制桌面端的 SQL 聚合**——规则仍只有一份。
- 如果 WebView 在某个屏幕真的顶不住（长列表、图表、后台），**按屏幕**引入 Kotlin 原生页；
  只有整个应用都顶不住时，才重新评估 React Native / 全原生。

### 同步的三层结构

同步不是一件事，是三层。**每层能独立交付、独立验证**，且互不阻塞：

| 层 | 负责什么 | 交付物 |
|---|---|---|
| **数据层** | 哪些实体可同步；每条记录带什么版本信息 | `rev` + 版本向量 + `deletedAt` 墓碑 |
| **传输层** | 字节怎么离开设备、怎么加密 | 加密容器文件 + 介质适配器 |
| **合并层** | 两份状态怎么合成一份 | 记录级合并算法（幂等、顺序无关） |

**合并层必须与传输层解耦**（不变量 10）：目录、WebDAV、GitHub 都只是把字节送到对端的管道，
合并逻辑完全不需要知道文件从哪来。新增一种网盘不碰合并逻辑，改合并策略也不碰传输。

### 数据层：可同步实体与记录级版本

| 实体 | 同步内容 | 注意 |
|---|---|---|
| 账户分类 / 收支分类 | 整条记录 + 树结构字段 | 分类树的父子关系随记录一起传；删除走墓碑 |
| 账户 | 整条记录 | 期初余额与期初日期是普通字段 |
| 交易 | 整条记录 + 金额/日期/类型/退款关联 | 核心实体 |
| 预算 | 整条记录 | 预算用量是派生值，不传 |
| 投资快照 | 整条记录（**前链不传**） | `previousSnapshotId` 本地按日期规则重算 |
| 变更日志 | 仅 S2 需要 | 见「同步形态的三个台阶」 |

**关键约束：容器格式与实体集合解耦。**

上面的表**不是封闭清单**。标签、多账本、周期规则、储蓄目标、票据这些实体
（推迟到阶段 4 的批次 K）将来也要同步。如果它们落地时需要改容器格式，
就等于两端一起返工。

因此容器里每条记录必须自带**类型标签**（`entityType` + `entityId`），
合并算法按「同一 `entityType` + 同一 `entityId`」判定同一条记录，
**不认识具体实体类型**。这样：

- 新增一种可同步实体 = **加一条类型标签 + 一种负载格式**，不改容器结构、不改合并算法。
- 读取端遇到不认识的 `entityType`：**跳过并记录警告**，不丢弃整批（丢弃整批会让
  一台旧设备挡住新设备的同步）。已识别的实体照常合并。
- `formatVersion` 变的是**容器结构**（加密、封装、分片），不是实体集合。

这条约束让「K 批次推迟」不产生同步返工，也让「K 批次落地」变成增量工作。

**用版本向量（vv）判断先后，不用时间戳**。每条可同步记录带两个东西：

- `rev`：本设备对该记录的本地修订号，每次本地修改 +1。
- `vv`：版本向量 `{deviceId: maxRev}`——写这条记录时，本设备在各设备上已知的最高修订号。

合并两条同 `id` 的记录时：

1. **可比**（A 的 vv 在每一维都 ≥ B 的 vv）→ A 是 B 的后继，取 A。**与时钟无关。**
2. **不可比**（各有对方没有的修订）→ 真并发修改 → 进冲突列表，**两个版本都保留**。
3. **vv 相同且内容相同** → 幂等，丢弃副本。

为什么不用时间戳：设备时钟可能偏差几小时，用 `updatedAt` 排序会让「先写的记录被后写的覆盖」——
钱会被静默改掉，而且用户无法察觉。为什么不用 `baseRev` 兜底：`baseRev` 只在增量日志里拿得到，
快照式同步没有它。版本向量两者都能覆盖，代价是每条记录几十字节。

### 传输层：加密容器 + 文件

**所有离开设备的字节都是加密容器**，全项目一种格式：

```text
container = header(formatVersion, ledgerId, kdf, salt, nonce) + ciphertext + tag
```

- 容器内是**记录流**：每个实体一条记录，带 `rev` / `vv` / `deletedAt`。
- 一条记录表达的是**结果状态**，不是操作指令（快照语义，不是命令语义）。
  因此同一份容器可以被重复应用、任意顺序应用，结果都一样（不变量 10）。
- AEAD：`XChaCha20-Poly1305`；AAD 绑定 `formatVersion|ledgerId`，防换头与跨账本重放。
- 密钥：`Argon2id(口令)`。**口令就是恢复码**——用户抄下来的那一串，不另设密码。
  同一账本的所有设备共用这一个口令，这是「多设备能互相解密」的前提。
  设备级独立密钥 + 共享密钥的两层结构推迟到出现共享账本时再做。
- 容器带 `formatVersion`，未知版本**拒绝整批**；坏记录不部分应用。
  **注意区分两个层级**：`formatVersion` 管的是**容器结构**（加密、封装、分片），
  未知结构无法安全解析，必须拒绝整批；而**记录级**的未知 `entityType`
  只跳过该条记录并警告（见「数据层」的实体集合解耦约束）——否则一台旧设备
  会挡住新设备的整个同步。

**加密威胁模型**：

- ✅ 防：网盘泄露、云服务商读取、传输窃听、备份文件被复制、GitHub 仓库泄露。
- ❌ 不防：设备被解锁后读取本地明文 SQLite、键盘记录、用户交出恢复码。
- 元数据仍会泄露：文件名、设备数量、文件大小、修改时间、同步频率。
  「端到端加密」不等于「什么都看不见」——设置页要写明这一点。
- 本地静态加密：当前是明文 SQLite + 操作系统磁盘加密 / 手机沙箱。
  SQLCipher 只在「设备丢失」成为真实威胁时做，且先证明迁移不丢数据。

### 传输适配：目录 / WebDAV / NAS / GitHub

| 介质 | 怎么用 | 成本 | 说明 |
|---|---|---|---|
| **本地目录** | 读目录下所有容器文件 | 最低 | OneDrive / Dropbox / iCloud / Nextcloud 客户端的同步目录；零 API、零 OAuth，**先用它验证协议本身** |
| **NAS** | 同目录，或 WebDAV | 低 | 群晖 / 威联通 / 飞牛都支持 WebDAV 或 SMB 挂载 |
| **WebDAV** | 列举 / 下载 / 上传 | 中 | 一个适配器覆盖多数自建与商用网盘 |
| **GitHub 私有仓库** | 每次同步提交一个容器文件；拉取时下载并合并 | 中 | **只做容器搬运，不做 Git 合并**（见下） |
| **厂商 API** | 同 WebDAV 但走 OAuth | 高 | 每家一套 OAuth、配额与审核，最后才做 |

**GitHub 的定位必须说清楚**：它能当网盘用——因为合并发生在记录层，
新设备就是多读几个容器文件，不需要 Git 的分支/合并语义。
但**不要把 Git 提交当成同步协议**：不依赖行级 diff，不做 Git 层面的冲突解法。
GitHub 的额外收益是每次同步留一个历史版本，等于免费获得时间旅行备份。
它不适合作实时同步的原因是延迟与配额，而不是协议不能做。

**NAS 值得单独强调**：它是「数据在用户手上」最纯粹的形态——文件在自己的硬盘上，
不经过任何云服务商，连元数据都不外泄；局域网内同步甚至不需要公网。

### 同步形态的三个台阶

不要一上来就做最难的。按收益/成本排序：

| 台阶 | 形态 | 用户看到什么 | 复杂度 | 什么时候做 |
|---|---|---|---|---|
| **S0 手动容器** | 「导出加密账本文件」→ 放到网盘/NAS → 另一台设备「导入」 | 能把账搬到另一台设备；丢数据能救 | 低：导出/导入 + 加密 + 合并 | M3 交付容器，M4 用它搬账 |
| **S1 自动目录同步** | 配一个目录，两端定时拉取/推送容器文件 | 两端自动收敛，不用手动 | 中：传输适配 + 合并 + 冲突界面 | M5 |
| **S2 增量变更日志** | 只传变化部分 | 大账本下传输量小 | 高：op log 落库 + `seq` 连续性 + 增量应用 | 账本 >10 万条或容器 >50MB 才做 |

**S0 就能验证最危险的部分**（加密容器格式、版本向量、合并算法、跨端测试向量），
却只花 S1 十分之一的成本。所以 S0 必须先做——它是 S1 的验收工具，不是过渡产品。
S0 拆在两个里程碑里：**M3 交付容器与合并算法**（PC 上可用、可导出可恢复），
**M4 交付跨设备搬运**（手机能装、能读桌面导出的容器）。

S2 才需要「每台设备只写自己的文件 `<ledgerId>/ops-<deviceId>.log`」这类增量日志设计：
那时才引入 `seq` 连续性检查、半写文件处理、op log 与业务写同事务落库。
在那之前，用整份容器覆盖是**更简单也更安全**的选择——不需要文件锁、不需要合并日志、
不会产生「冲突副本」，而且天然幂等。

### 自动记账（Android 通知采集）

**承诺的是「通知辅助记账」，不是「全自动记账」。**

```text
通知 → 允许列表内的支付/银行 App → 本地解析 → 候选收件箱 → 去重 → 用户确认 → 正常交易写入
```

- 采集与账务分离：候选不是交易，不参与余额与报表；确认前不进账本。
- v1 不自动入账。按商户的学习规则，只在解析准确率被真实数据证明、且用户显式开启后才做。
- 只生成支出候选；退款/转账/收入的通知语义不可靠，不自动生成。
- 去重复用 `importKey`（`notify:<包名>:<稳定哈希>`），并与同金额、同时间附近的已有交易比对，
  避免「手动记过又自动记一遍」。
- 原始通知文本只在设备本地、只在候选期保留（默认 7 天），不进同步、不进备份、不进日志；
  只保存解析后的金额/商户/时间/来源。
- 通知可能被系统折叠、内容隐藏、App 根本不发、厂商杀后台；解析失败必须在收件箱可见，
  不能静默丢弃。Google Play 对通知监听权限有披露与审核要求，可能拒绝；sideload 是备选。
- 回退：没有权限或解析不了时，保留手动快速记账与「分享到 MoneyBrain」入口。

### 同步对现有模型的要求（由批次 F 补齐）

| 要求 | 现状 | 动作 |
|---|---|---|
| 客户端生成 ID | Prisma `@default(uuid())`，离线创建没有 ID | 所有可同步实体由客户端生成 UUID，服务端不再代生成 |
| 修改版本 | `Transaction` 只有 `createdAt`，没有 `updatedAt`；其它表有 `updatedAt` | 所有可同步实体补 `updatedAt` + `rev` + `vv`（版本向量） |
| 删除墓碑 | 硬删除（B2 改软删除） | `deletedAt` 随记录传播；快照式同步天然携带墓碑 |
| 账本与设备标识 | 无 | `ledgerId`、`deviceId`（设备首次注册时生成并持久化） |
| 派生字段 | 投资快照 `previousSnapshotId` 落库但属于派生链 | 不写入同步记录；应用后按日期规则重算 |
| 同步排序 | 依赖时间戳 | 用版本向量判定先后，**不用设备时钟**（时钟可能偏差几小时） |

### 这一层明确不做

自建服务器、账号体系、共享账本（多人共用一本账）、实时协作、CRDT、
把 SQLite 文件直接放网盘（会被网盘客户端写坏）、Git 层面的合并与冲突解法、
厂商 OAuth 全家桶、本地库端到端加密（本地明文是明确边界）。

**关于 GitHub**：它**是**受支持的同步介质之一（见「传输适配」表），
只是不承担「同步协议」的职责——不做 Git 分支合并、不做行级 diff。


## 差距清单

### 批次 F · 同步就绪契约（PC，先于移动端）

只改数据契约与本地能力，**不接网盘、不做传输**。这一批是移动端与同步的共同地基。

| # | 现状 | 目标 | 验收 |
|---|---|---|---|
| F1 | ID 由 Prisma 生成，离线创建没有 ID | 所有可同步实体由客户端生成 UUID | 断网创建后补写库不换 ID；同一 ID 导入不重复 |
| F2 | `Transaction` 没有 `updatedAt`；没有删除墓碑 | 所有可同步实体补 `updatedAt` + `rev` + `vv`；B2 的 `deletedAt` 复用 | 每次写入 `rev` 递增、`vv` 更新；删除产生墓碑 |
| F3 | 账本与设备无标识 | `ledgerId` + `deviceId`（首次注册生成并持久化） | 两台设备各有稳定 `deviceId`；容器 AAD 绑定 `ledgerId` |
| F4 | 无版本向量合并 | 实现记录级合并算法（vv 可比取后者 / 不可比进冲突表 / 相同幂等丢弃） | 同一组记录**任意顺序**应用两次，结果逐字段一致（不变量 10） |
| F5 | 无加密容器 | 加密账本容器（`formatVersion` + Argon2id + XChaCha20-Poly1305）+ 恢复码 | 错误口令失败关闭；文件内无明文；`db:drill` 仍通过 |
| F6 | 投资快照前链落库 | 前链不写入同步记录，应用后重算 | 同步不复制 `previousSnapshotId`，重算结果与原链一致 |
| F7 | 无格式版本与校验 | 容器与备份格式带 `formatVersion`，逐条运行时校验 | 未知版本拒绝整批；坏记录不部分应用 |
| F8 | 无跨端测试向量 | 固定测试向量：同一口令、同一明文在 Node 与 WebView 都能解开 | CI 跑同一组向量，两端结果一致 |
| F9 | 备份是明文 ZIP | 备份与同步共用**同一个加密容器格式** | 备份文件可被同步引擎读取；不存在第二份加密实现 |
| F10 | 容器格式只存在于代码里 | 容器格式**公开且可独立实现**：格式说明文档 + 参考解密脚本 | 用文档里的参数在项目外解开一份容器；格式变更走 `formatVersion` |
| F11 | 容器格式与实体集合耦合，新增可同步实体要改容器与合并算法 | 记录自带 `entityType` + `entityId`；合并算法不识别具体实体类型；不认识类型跳过并警告 | 往容器里塞一条未知 `entityType` 的记录：已识别实体照常合并，未知记录被跳过并有警告，无整批失败；新增实体类型不需要改合并算法 |

**单账本阶段的 `ledgerId` 是什么**（多账本推迟到阶段 4 · K3，这里必须先说清）：

`ledgerId` 在 K3 落地前**不代表「用户建的第几本账」**，它是「这个账本实例的身份」——
由客户端在首次注册时生成的持久化 UUID，作用是：

- 绑定 AAD，防止别的账本的容器被拿来解密或重放到本账本。
- 标识同步数据集的归属，让两台设备确认「我们在同步同一本账」。

K3 落地后，`ledgerId` 从「一个固定值」变成「账本表的主键」——**字段含义不变，变的是它指向
一个还是多个**。所以现在就定义它不会返工，反而是推迟定义才会返工。

### 批次 G · 加密同步（S0 手动 → S1 自动）

分两段交付：**S0 先让人能跨设备搬账，S1 再自动化**。

| # | 现状 | 目标 | 验收 |
|---|---|---|---|
| G1 | 只能手动导出明文备份 | **S0**：导出/导入加密账本文件到任意目录 | 桌面导出的容器，手机能导入并得到相同余额；反向亦然 |
| G2 | 无传输适配 | **S1**：传输适配器（本地目录 / WebDAV / NAS / GitHub 同一接口） | 换介质只换适配器，合并逻辑与同步代码零改动（不变量 10） |
| G3 | 无自动同步 | 变更后/定时同步 + 真实状态指示 | 断网、失败、待上传、冲突四种状态都可见；失败不伪装成成功 |
| G4 | 无冲突处理 | 冲突表 + 待确认界面 + 保留双方版本 | 并发改同一笔时不重复计钱；用户能选或合并 |
| G5 | 无同步自检 | 应用前自动快照 + `npm run sync:drill` | 同步后 `db:verify` 恒过；失败可一键回滚 |
| G6 | 无恢复流程 | 新设备：恢复码 → 下载 → 解密 → 合并 | 空设备 10 分钟内恢复出同样余额 |
| G7 | GitHub 定位不清 | GitHub 作为**容器搬运介质**（每次同步提交一个加密容器） | GitHub 仓库被clone 下来能独立恢复账本；不做 Git 层面合并 |

## 出口条件

- 加密容器可导出可导入；错误口令失败关闭；文件内无明文账务数据。
- 同一组记录**任意顺序**应用两次，结果逐字段一致。
- 备份与同步共用同一套加密，不存在第二份加密实现。
- 容器格式公开可解：用文档里的参数能在项目外解开一份容器。
- 网盘 / NAS / GitHub 任一介质都能同步；冲突可见且不重复计钱。
- 同步后 `db:verify` 恒过；失败可一键回滚。
- 新设备 10 分钟内恢复出同样余额。

## 本阶段不做

多用户共享账本、设备级密钥轮换、增量变更日志（S2）——触发条件出现才做，
见 [principles.md](principles.md) 的候选功能池。
