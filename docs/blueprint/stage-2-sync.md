# 阶段 2 · 同步（M3–M5）

> **目标**：让两台设备上的账自动收敛，且**用户不失去对自己数据的控制**——
> 文件在自己的网盘/NAS 上，密钥自己拿着，没有账号、没有服务器、没有云厂商。
>
> 这一阶段的产物是手机端与桌面端的共同契约，因此**必须在移动端之前**。

## 本阶段要解决的问题

问题集中在三处：数据契约的身份与版本（F1–F4、F8；已由 F-A 落地）、加密容器与格式（F5–F11）、传输与冲突/恢复（G1–G8）；逐条映射见下方差距清单。

## 同步架构

这一节是整个蓝图的架构核心。**先读懂它，再动手**——
同步的 bug 会直接表现为"两台设备数字不一样"，那是最伤信任的一类问题。

### 端拓扑

```text
桌面：apps/web → apps/api(HTTP) → app 用例 → Prisma/SQLite
手机：apps/mobile(Capacitor + React) → app 用例 → SQLite（手机本地）
共享：domain（算钱）· contracts（类型）· app（用例/仓储端口）· sync（加密/合并/应用）
同步：用户自己的网盘 / NAS / GitHub ↔ 加密账本容器 ↔ 每台设备的本地账本
```

- **桌面**：现有 React + Vite + Express + Prisma 全部保留，是第一客户端，也是规则验证场。
- **手机**：Capacitor + 现有 React 构建产物 + Kotlin 原生模块（通知监听、文件与密钥访问）。
  手机不跑 Express/Prisma，只实现 SQLite 仓储适配器。移动端按 UX3 的平台差异规范单独设计，
  不沿用桌面响应式缩放（决策 #36）；只有实测不达标时才针对屏幕引入移动控件，不引入第二套 UI 库。
- **复用与降级**：手机复用 **R2c 重建后的** feature/query 层（`services/api.ts` 换成本地仓储适配器 + 相同响应信封），
  报表直接调领域层纯函数，**不复制桌面 SQL 聚合**。WebView 在某个屏幕顶不住时**按屏幕**引入 Kotlin 原生页；
  只有整个应用都顶不住，才重新评估 React Native / 全原生。iOS / iPad 复用 UI/用例/领域层，通知自动记账不承诺。

### 同步的三层结构

同步不是一件事，是三层。**每层能独立交付、独立验证**，且互不阻塞：

| 层 | 负责什么 | 交付物 |
|---|---|---|
| **数据层** | 哪些实体可同步；每条记录带什么版本信息 | `rev` + 版本向量 + `deletedAt` 墓碑 |
| **传输层** | 字节怎么离开设备、怎么加密 | 加密容器文件 + 介质适配器 |
| **合并层** | 两份状态怎么合成一份 | 记录级合并算法（幂等、顺序无关） |

**合并层必须与传输层解耦**（不变量 10）：目录、WebDAV、GitHub 都只是把字节送到对端的管道，
合并逻辑完全不需要知道文件从哪来。新增一种网盘不碰合并逻辑，改合并策略也不碰传输。

### 数据层：可同步实体与记录级版本

| 实体 | 同步内容 | 注意 |
|---|---|---|
| 账户分类 / 收支分类 | 整条记录 + 树结构字段 | 分类树的父子关系随记录一起传；删除走墓碑 |
| 账户 | 整条记录 | 期初余额与期初日期是普通字段 |
| 交易 | 整条记录 + 金额/日期/类型/退款关联 | 核心实体 |
| 预算 | 整条记录 | 预算用量是派生值，不传 |
| 投资快照 | 整条记录（**前链不传**） | `previousSnapshotId` 本地按日期规则重算 |
| 变更日志 | 仅 S2 需要 | 见「同步形态的三个台阶」 |

**关键约束：容器格式与实体集合解耦。**

上面的表**不是封闭清单**。标签、多账本、周期规则、储蓄目标、票据这些实体
（推迟到阶段 4 的批次 K）将来也要同步。如果它们落地时需要改容器格式，就等于两端一起返工。

因此容器里每条记录必须自带**类型标签**（`entityType` + `entityId`），
合并算法按「同一 `entityType` + 同一 `entityId`」判定同一条记录，**不认识具体实体类型**。这样：

- 新增一种可同步实体 = **加一条类型标签 + 一种负载格式**，不改容器结构、不改合并算法。
- 读取端遇到不认识的 `entityType`：**跳过并记录警告**，不丢弃整批（丢弃整批会让
  一台旧设备挡住新设备的同步）。已识别的实体照常合并。
- `formatVersion` 变的是**容器结构**（加密、封装、分片），不是实体集合。

**用版本向量（vv）判断先后，不用时间戳**。每条可同步记录带两个东西：

- `rev`：本设备对该记录的本地修订号，每次本地修改 +1。
- `vv`：版本向量 `{deviceId: maxRev}`——写这条记录时，本设备在各设备上已知的最高修订号。

合并两条同 `id` 的记录时：

1. **可比**（A 的 vv 在每一维都 ≥ B 的 vv）→ A 是 B 的后继，取 A。**与时钟无关。**
2. **不可比**（各有对方没有的修订）→ 真并发修改 → 进冲突表，**两个版本都保留**（见下）。
3. **vv 相同且内容相同** → 幂等，丢弃副本。

**冲突的存储与收敛**（F4/G4 的实现规格，没有它冲突处理无法落地）：

- **存储**：本地表 `sync_conflicts(id, entityType, entityId, versionA, versionB, detectedAt, resolvedAt)`。
  它是**设备本地表，不进容器、不参与同步**——冲突在每台设备上独立检出。
  输的那一版**必须落在这张表里**，不能只在内存或临时状态：每台设备整份覆盖自己的容器文件，
  只留内存的话，下一次导出就把输的那版永久丢掉了（违反不变量 8「另一版本必须留存」）。
- **收敛**：用户解决冲突（选一方或手动合并）后，**写一条新记录**——
  `rev` = 双方较大值 + 1；`vv` = 双方逐维取最大（本设备维随之 ≥ 新 `rev`）。
  新 `vv` 在每一维都 ≥ 两个旧版本，因此**同时支配双方**：
  其它设备应用这条记录后，旧冲突的两个版本都变成可比的前驱，同一冲突**不会在另一端再次弹出**。
  写完后把 `sync_conflicts` 行标记 `resolvedAt`，已解决的冲突行保留一段时间供界面回溯，不随容器传播。

不用时间戳的理由见决策 #25；不用 `baseRev` 兜底，是因为它只在增量日志里拿得到，快照式同步没有它。
版本向量两者都能覆盖，代价是每条记录几十字节。

### 传输层：加密容器 + 文件

**所有离开设备的字节都是加密容器**，全项目一种格式：

```text
container = header(formatVersion, ledgerId, kdf, salt, nonce) + ciphertext + tag
```

**加密粒度写死：整包一个 AEAD**（header 之后全部明文一次加密、一个 tag）。
不做逐条 AEAD——逐条方案需要 per-record nonce、记录总数与最终 MAC 才能发现截断，
复杂度不成比例；整包 AEAD 下文件被截断、半写或篡改时 tag 校验直接失败，**拒绝整批**，
不存在「静默丢尾部几条」的问题。

- 容器内是**记录流**：每个实体一条记录，带 `rev` / `vv` / `deletedAt`。
- **每台设备只写自己的容器文件**（`<ledgerId>/container-<deviceId>.bin`），
  读取目录下**其它设备的**容器文件做合并。两台设备**永不写同一个文件**——
  否则网盘客户端会在文件层产生冲突副本或静默覆盖，这是文件级同步的老坑，
  从命名上根除它（记录层的合并不受影响，仍是幂等、顺序无关的）。
- 一条记录表达的是**结果状态**，不是操作指令（快照语义，不是命令语义）。
  因此同一份容器可以被重复应用、任意顺序应用，结果都一样（不变量 10）。
- AEAD：`XChaCha20-Poly1305`；AAD 绑定 `formatVersion|ledgerId`，防换头与跨账本重放。
  **实现库在 F5 落地时点名锁定**：WebCrypto 与 Node 内置 `crypto` 都没有 XChaCha20-Poly1305
  与 Argon2id，必须引入 WASM / 原生库（候选：`libsodium-wrappers`，或 `@noble/ciphers` +
  Argon2 WASM）。库体积与初始化耗时计入 V3 的真机冷启动验收——这必须在容器格式冻结前验证。
- 密钥：`Argon2id(恢复码)`。**恢复码由系统生成（≥128 位熵，如 Base32 编码 + 分组显示），
  用户抄写保管，不支持用户自选口令**——自选口令无法保证熵，且 UI 与 KDF 参数完全不同。
  恢复码同时是备份容器与同步容器的唯一口令，同一账本的所有设备共用，
  这是「多设备能互相解密」的前提。设备级独立密钥 + 共享密钥的两层结构推迟到出现共享账本时再做。
- **恢复码轮换（G8）**：解密全部容器与备份 → 用新恢复码重新加密 → 删除本地旧文件。
  已复制到别处的旧文件无法召回，界面必须写明这一点；换码后旧码对新容器解密失败。
- 容器带 `formatVersion`，未知版本**拒绝整批**；坏记录不部分应用。
  **注意区分两个层级**：`formatVersion` 管的是**容器结构**，未知结构无法安全解析，必须拒绝整批；
  而**记录级**的未知 `entityType` 只跳过该条记录并警告（见「数据层」），
  否则一台旧设备会挡住新设备的整个同步。

**加密威胁模型**：

- ✅ 防：网盘泄露、云服务商读取、传输窃听、备份文件被复制、GitHub 仓库泄露。
- ❌ 不防：设备被解锁后读取本地明文 SQLite、键盘记录、用户交出恢复码。本地静态加密当前是
  明文 SQLite + 操作系统磁盘加密 / 手机沙箱；SQLCipher 只在「设备丢失」成为真实威胁时做。
- 元数据仍会泄露：文件名、设备数量、文件大小、修改时间、同步频率。「端到端加密」不等于
  「什么都看不见」——设置页要写明这一点。

### 传输适配：目录 / WebDAV / NAS / GitHub

| 介质 | 怎么用 | 成本 | 说明 |
|---|---|---|---|
| **本地目录** | 读目录下所有容器文件 | 最低 | OneDrive / Dropbox / iCloud / Nextcloud 客户端的同步目录；零 API、零 OAuth，**先用它验证协议本身** |
| **NAS** | 同目录，或 WebDAV | 低 | 群晖 / 威联通 / 飞牛都支持 WebDAV 或 SMB 挂载 |
| **WebDAV** | 列举 / 下载 / 上传 | 中 | 一个适配器覆盖多数自建与商用网盘 |
| **GitHub 私有仓库** | 每次同步提交一个容器文件；拉取时下载并合并 | 中 | **只做容器搬运，不做 Git 合并** |

**GitHub 的定位必须说清楚**：它能当网盘用——因为合并发生在记录层，新设备就是多读几个容器文件，
不需要 Git 的分支/合并语义。但**不要把 Git 提交当成同步协议**：不依赖行级 diff，不做 Git 层面的
冲突解法。额外收益是每次同步留一个历史版本；不适合作实时同步的原因是延迟与配额，不是协议不能做。
厂商 API 最后才做（每家一套 OAuth、配额与审核）。

**NAS 值得单独强调**：它是「数据在用户手上」最纯粹的形态——文件在自己的硬盘上，不经过任何云服务商，
连元数据都不外泄；局域网内同步甚至不需要公网。

### 同步形态的三个台阶

不要一上来就做最难的。按收益/成本排序：

| 台阶 | 形态 | 用户看到什么 | 复杂度 | 什么时候做 |
|---|---|---|---|---|
| **S0 手动容器** | 「导出加密账本文件」→ 放到网盘/NAS → 另一台设备「导入」 | 能把账搬到另一台设备；丢数据能救 | 低：导出/导入 + 加密 + 合并 | M3 交付容器，M4 用它搬账 |
| **S1 自动目录同步** | 配一个目录，每台设备只写自己的容器文件，定时拉取目录下全部设备文件做合并 | 两端自动收敛，不用手动 | 中：传输适配 + 合并 + 冲突界面 | M5 |
| **S2 增量变更日志** | 只传变化部分 | 大账本下传输量小 | 高：op log 落库 + `seq` 连续性 + 增量应用 | 账本 >10 万条或容器 >50MB 才做 |

**S0 就能验证最危险的部分**（容器格式、版本向量、合并算法、跨端向量），却只花 S1 十分之一的成本：
它是 S1 的验收工具，不是过渡产品。M3 交付容器与合并算法，M4 交付跨设备搬运。

S2 才需要增量日志设计（`<ledgerId>/ops-<deviceId>.log` + `seq` 连续性 + 半写处理 + 与业务写同事务）；
在那之前，S0/S1 用「每设备一份容器文件 + 整份覆盖」更简单也更安全——无需文件锁与合并日志，天然幂等。

### 自动记账（Android 通知采集）

**承诺的是「通知辅助记账」，不是「全自动记账」**；实现条目见 [stage-3](stage-3-mobile.md) 批次 I。

```text
通知 → 允许列表内的支付/银行 App → 本地解析 → 候选收件箱 → 去重 → 用户确认 → 正常交易写入
```

架构上的硬约束（批次 I 不再复述）：候选不是交易，确认前不进账本、不参与余额与报表；v1 不自动入账；
**只生成支出候选**；去重键 `notify:<包名>:<稳定哈希>`，并与同金额、同时间附近的已有交易比对；
原始通知文本只在设备本地保留 ≤7 天，不进同步/备份/日志；解析失败必须在收件箱可见；
Play 审核可能拒绝，sideload 是备选；无权限时保留手动快速记账与分享入口。

### 对现有模型的要求

F-A/F-B 已落地：客户端生成 ID 与 `rev`/`vv`、`deletedAt` 墓碑、`ledgerId`/`deviceId`；
记录级合并已按版本向量判定先后（**不用设备时钟**）。仍未做的是前链不入同步记录、
应用后重算（F-C）。

### 这一层明确不做

自建服务器、账号体系、共享账本、实时协作、CRDT；把 SQLite 文件直接放网盘；Git 层面的合并与
冲突解法；厂商 OAuth 全家桶；本地库端到端加密（本地明文是明确边界）。

## 差距清单

### 批次 F · 同步就绪契约（PC，先于移动端）

只改数据契约与本地能力，**不接网盘、不做传输**。这一批是移动端与同步的共同地基。
F1–F11 按三包推进（每包 1–2 次会话），包内条目同批验收。

| # | 覆盖 | 现状 → 目标 | 验收 |
|---|---|---|---|
| F-C | F5–F7、F9–F11 | 无加密容器；前链落库；无格式版本与校验；备份是明文 ZIP；容器格式只存在于代码里；容器与实体集合耦合 → `formatVersion` + Argon2id + XChaCha20-Poly1305 + 系统生成恢复码（落地时点名锁定加密库）；前链不写入同步记录、应用后重算；逐条运行时校验；备份与同步共用同一容器；格式说明文档 + 参考解密脚本；记录自带 `entityType` + `entityId`，合并不识别具体类型 | 错误恢复码失败关闭；文件内无明文；`db:drill` 仍通过；跨端与初始化开销在 F8/V3 验证通过后才冻结容器格式；同步不复制 `previousSnapshotId` 且重算与原链一致；未知版本拒绝整批、坏记录不部分应用；备份文件可被同步引擎读取、不存在第二份加密实现；用文档参数能在项目外解开一份容器；未知 `entityType` 跳过并警告、已识别实体照常合并、无整批失败；新增实体类型不需要改合并算法 |

**合并时的引用完整性**（F4 验收的一部分，快照语义下必然出现中间态）：

容器按设备分文件到达，应用某一份时，它引用的对象可能不在本批——
要么还在别的设备文件里（尚未拉取），要么已被另一台设备删除（墓碑）：

- **引用悬空（暂时）**：指向的记录本批未见 → 进入「待补全」：**不入账、不参与余额与报表**；
  后续文件补齐后自动转为正常记录。
- **引用已被删除**：以墓碑为准，同样「待补全」并在界面提示用户处理（改指向或删除），**不静默复活**。
- **`db:verify` 的运行时点**：目录下还有未应用容器时「待补全」不算失败；全部应用完毕后必须恒过。

**单账本阶段的 `ledgerId` 是什么**（多账本推迟到阶段 4 · K3，这里必须先说清）：

`ledgerId` 在 K3 落地前不是「用户建的第几本账」，而是「这个账本实例的身份」——首次注册生成的
持久化 UUID，绑定 AAD（防跨账本重放）并标识同步数据集归属。K3 落地后它变成「账本表的主键」，
**字段含义不变，变的是指向一个还是多个**；现在定义不会返工，推迟定义才会。

### 批次 G · 加密同步（S0 手动 → S1 自动）

分两段交付：**S0 先让人能跨设备搬账，S1 再自动化**。G1/G6 属 M4，G2–G5/G8 属 M5。

| # | 覆盖 | 现状 → 目标 | 验收 |
|---|---|---|---|
| G-A | G1、G6 | 只能手动导出明文备份；无恢复流程 → **S0** 导出/导入加密账本文件到任意目录；新设备「恢复码 → 下载 → 解密 → 合并」 | 桌面导出的容器，手机能导入并得到相同余额；反向亦然；空设备 10 分钟内恢复出同样余额 |

## 验收基线

- 加密容器可导出可导入；错误口令失败关闭；文件内无明文账务数据。
- 同一组记录**任意顺序**应用两次，结果逐字段一致。
- 备份与同步共用同一套加密，不存在第二份加密实现。
- 容器格式公开可解：用文档里的参数能在项目外解开一份容器。
- 网盘 / NAS / GitHub 任一介质都能同步；冲突可见且不重复计钱；解决冲突后另一端不复现同一冲突。
- 恢复码可更换（G8）：换码后旧码解不开新容器。
- 同步后 `db:verify` 恒过；失败可一键回滚。
- 新设备 10 分钟内恢复出同样余额。

## 本阶段不做

多用户共享账本、设备级密钥轮换、增量变更日志（S2）——触发条件出现才做，
见 [stage-4](stage-4-expansion.md) 的候选功能池。
