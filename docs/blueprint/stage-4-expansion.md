# 阶段 4 · 延后功能与按需扩展（M7）

> **目标**：把已经长成的产品扩展到更多场景。
> 这一阶段的条目**要么是明确推迟的**，**要么都有触发条件**——条件不出现就不开工。
>
> **阶段 1 只留 K8（桌面壳），K1–K7 全部推迟到这里。**
> 推迟不是取消：这些功能的价值没有下降，只是**现在做它会让界面与体验的债变贵**。
> 详见入口文档的「关键依赖」。

## 差距清单

### 批次 K · PC 产品补全（从阶段 1 推迟）

**这一批决定「PC 端可用」到底是什么**，原本排在移动端之前。
现在推迟到阶段 4，理由与代价见下。

| # | 现状 | 目标 | 验收 | 触发条件 |
|---|---|---|---|---|
| K1 | 只能手动记单笔 | 周期交易（房租、订阅、工资）：按规则自动生成待确认交易 | 按规则生成、生成前可预览、金额可变、生成后成为普通交易可编辑 | 用户抱怨「每月都要重录」 |
| K2 | 只有分类，没有标签 | 标签（多对多）：一笔交易可打多个标签 | 标签可增删改、筛选按标签、标签随同步传播 | 需要「一笔钱多个维度」的归类 |
| K3 | 无账本概念 | 多账本（个人 / 家庭 / 公司各一本），每本独立 | 账本可切换、独立统计、账本 ID 写入同步容器 | 出现「个人与公司的钱要分开」的需求 |
| K4 | 只能通过账户余额看数 | 目标储蓄（攒钱目标）：进度条 + 还需每月存多少 | 目标可设金额与期限；进度按分类支出自动算 | 用户在用其它工具记攒钱目标 |
| K5 | 无票据 | 交易可附票据图片（拍照或选图），压缩后随记录同步 | 票据可看可删；不计入金额；单图大小有上限 | 票据留存成为真实需求 |
| K6 | 只能整本备份 | 按范围备份/导出（账户、分类、交易、附件） | 范围导出后可单独恢复，不影响其它数据 | 大账本导出耗时变长 |
| K7 | 无「下期应付」概念 | 待付款清单（已承诺未支付），从周期交易派生 | 待付款可标记已付，标记后生成正式交易 | 随 K1 一起来 |

**为什么推迟**：

- 界面层的债会随新增功能**变得更贵**。新增功能要么复用现有组件，要么新增组件——
  两种都要求现有组件是统一的。先在统一的地基上加功能，比在 320 处内联样式里再加功能便宜。
- 「PC 端可用」的门槛里，真正卡住用户的是**界面不可信**（点不动、看不见焦点、暗色看不清），
  不是少了周期交易。K8（能装能启动）+ 阶段 1 的界面治理，收益远大于 K1–K7。
- **推迟的代价是真实的**：手机端要同步的对象不再是一个「功能完整」的 PC 产品。
  这个代价由「同步契约与实体集合解耦」来兜（见入口文档的「关键依赖」）。

**什么时候必须回来做**：K1/K2/K3 不是「想做就做」——它们决定可同步实体的集合。
若在它们落地前同步契约已经定型，这三个功能落地时必须回头改容器格式与两端代码。
因此**只要开始做这三条中的任意一条，就要先确认同步契约的扩展方式**（见批次 F 的验收）。

### 批次 J · 按需扩展（不进主线）

| # | 内容 | 触发条件 |
|---|---|---|
| J1 | i18n 完整接入：语言切换 UI + `en-US` 目录（文案目录与查表函数已在阶段 1 建好） | 真的要上第二种语言 |
| J2 | iOS / iPad | Android 验证通过且确有 iOS 需求；自动记账不承诺 |
| J3 | Drive / Dropbox 等厂商 API | 目录与 WebDAV 在目标设备不可行 |
| J4 | SQLCipher 本地加密 | 设备丢失成为真实威胁 |

> 这几项**技术方案已明确，只等触发条件**。方向都还没定的构想见下面的候选功能池。

## 候选功能池（还没立项，触发条件出现才做）

这些是「可能需要、但现在没有明确需求」的功能。**不是承诺**，是备选池。
技术方案已明确、只等触发条件的（iOS、SQLCipher、厂商 API、i18n 完整接入）见批次 J。

| # | 功能 | 价值假设 | 触发条件 |
|---|---|---|---|
| P1 | 共享账本（多人一本账） | 家庭共同记账 | 单人模式被明确抱怨；需要权限模型 |
| P2 | 银行流水自动导入 | 免去手工导入 | 用户抱怨导入麻烦；需要银行适配与凭证处理 |
| P3 | 多币种估值 | 海外账户 | 出现真实外币账户（语言需求不算） |
| P4 | 桌面小部件 / 快捷键 | 记账频次高的用户 | 记账被高频使用（每周 >20 笔） |
| P5 | 发票 OCR | 自动填金额 | 票据功能被高频使用 |
| P6 | 复式记账（可配科目表） | 专业会计需求 | 出现明确的专业用户 |
| P7 | 现金流预测 | 提前知道够不够花 | 预算与报表被高频使用 |
| P8 | 订阅制支出聚合 | 看清订阅总花费 | 周期交易被高频使用 |
| P9 | **用户层面对账**（拿银行流水核对账本差异） | 数字可信，不只是自洽 | 用户抱怨「余额和银行对不上」；需要银行流水导入 |
| P10 | **分账**（AA 记账，一笔支出拆给多人） | 聚餐、团建等场景 | 出现多用户诉求但暂不共享账本 |

**P1/P6/P3 会推翻大量现有设计**，真要做时应当重新评估而不是直接开工。

## 先验证的 spike

在承诺对应里程碑之前先做，失败就换方案，不把风险留到主线。
编号用 `V`（验证），与候选功能池的 `P` 区分开。

| # | 问题 | 时间盒 | 通过标准 | 失败就 |
|---|---|---|---|---|
| V1 | 桌面一键启动（Tauri）能包住现有 Express + Prisma 吗？ | 1–2 天 | 双击启动、可选开机自启、数据目录可迁移 | 回退到「启动脚本 + 浏览器」 |
| V2 | Capacitor + 现有 Vite 构建 + AntD 响应式布局在目标 Android 真机可用吗？ | 1–2 天 | 记账表单、列表、首页可操作；冷启动 <2s | 按屏幕引入移动控件/原生页，不改领域层 |
| V3 | 手机 WebView 里 SQLite 插件 + 共享领域层能跑通吗？ | 1–2 天 | 5k 笔查询 <100ms；事务写入可用 | 换 SQLite 插件或原生仓储适配器 |
| V4 | 目标机型能稳定读到支付通知吗？ | 1 天 | 允许列表内能拿到金额/商户；可去重 | 降级为「分享到 MoneyBrain」+ 手动记账 |
| V5 | 加密容器 + 版本向量合并 + 两实例目录同步能收敛吗？ | 2–3 天 | 两实例一致；乱序/重复/半文件都不出错；KDF <2s | 换 KDF 或重设计协议，先不上传输 |

V1 在阶段 1（M2）期间做；V2–V4 在阶段 0/M1 期间穿插做；V5 在 M3 开头做。
每个 spike 结束写一段结论进本文或 ADR，不保留演示代码。

## 主要风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 低端 Android 上 WebView + AntD 卡顿 | 记账体验不可用 | V2 真机实测；按屏幕降级，不整体重写 |
| 通知权限被厂商 ROM 限制 / Play 审核拒绝 | 自动记账不可用 | V4 验证；保留手动与分享回退；sideload 备选 |
| 手机/平板访问不到「已同步目录」 | 同步不可用 | WebDAV / NAS 适配器；仍不行才做厂商 API |
| 用户丢失恢复码 | 数据永久不可解 | 强制抄写 + 新设备恢复演练 + 界面明确说明无找回 |
| 冲突处理把两个版本都入账 | 重复计钱 | 不变量 8 + 专项测试；同一 `entityId` 只应用一个版本 |
| 设备时钟偏差导致覆盖错版本 | 数字被静默改掉 | 用版本向量而非时间戳排序（不变量 10） |
| 桌面与手机各写一套规则 | 数字分叉 | 共享 `app`/`domain`；跨端测试向量；合并后 `db:verify` 恒过 |
| 容器文件损坏或只同步到一半 | 数据分叉 | 逐条 AEAD + `formatVersion` 校验 + 原子重命名 + 拒绝整批应用 |
| 网盘客户端改写文件导致容器损坏 | 同步不可用 | 临时文件 + 原子改名；校验失败不应用 |
| 容器体积无界增长 | 同步变慢 | S0/S1 接受（个人规模几 MB）；>50MB 才做增量日志（S2） |
| 用户以为「端到端加密」连本地也加密 | 安全预期错误 | 威胁模型写进设置页；本地明文是明确边界 |
| Tauri 包不住 Express + Prisma | PC 端装不起来 | V1 先验证；失败回退到启动脚本 + 浏览器，不硬凑 |
| **K 批次一直推迟，手机端同步到半个产品** | 移动端价值打折 | 同步契约与实体集合解耦（批次 F 验收）；手机端只同步当期存在的实体，不假装支持还不存在的功能 |

每个里程碑结束都要能回答四个问题：**这笔钱在 5 个视图里是否一致？断网还能不能记账？
两台设备冲突时会不会重复计钱？换一台空设备能不能恢复出同样的余额？**
