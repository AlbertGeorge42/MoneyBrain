# 阶段 4 · 多语言与按需扩展（M7）

> **目标**：把已经长成的产品扩展到更多场景与更多语言。
> 这一阶段的条目**都有触发条件**——条件不出现就不开工。

## 差距清单

### 批次 J · 按需扩展（不进主线）

| # | 内容 | 触发条件 |
|---|---|---|
| J1 | i18n 框架接入（文案目录已建，只差查表函数与翻译） | 真的要上第二种语言 |
| J2 | iOS / iPad | Android 验证通过且确有 iOS 需求；自动记账不承诺 |
| J3 | Drive / Dropbox 等厂商 API | 目录与 WebDAV 在目标设备不可行 |
| J4 | SQLCipher 本地加密 | 设备丢失成为真实威胁 |

> 这几项**技术方案已明确，只等触发条件**。方向都还没定的构想见 §5.4 候选功能池。

### 候选功能池（还没立项，触发条件出现才做）

这些是「可能需要、但现在没有明确需求」的功能。**不是承诺**，是备选池。
技术方案已明确、只等触发条件的（iOS、SQLCipher、厂商 API、i18n）见批次 J。

| # | 功能 | 价值假设 | 触发条件 |
|---|---|---|---|
| P1 | 共享账本（多人一本账） | 家庭共同记账 | 单人模式被明确抱怨；需要权限模型 |
| P2 | 银行流水自动导入 | 免去手工导入 | 用户抱怨导入麻烦；需要银行适配与凭证处理 |
| P3 | 多币种估值 | 海外账户 | 出现真实外币账户（语言需求不算） |
| P4 | 桌面小部件 / 快捷键 | 记账频次高的用户 | 记账被高频使用（每周 >20 笔） |
| P5 | 发票 OCR | 自动填金额 | 票据功能被高频使用 |
| P6 | 复式记账（可配科目表） | 专业会计需求 | 出现明确的专业用户 |
| P7 | 现金流预测 | 提前知道够不够花 | 预算与报表被高频使用 |
| P8 | 订阅制支出聚合 | 看清订阅总花费 | 周期交易被高频使用 |
| P9 | **用户层面对账**（拿银行流水核对账本差异） | 数字可信，不只是自洽 | 用户抱怨「余额和银行对不上」；需要银行流水导入 |
| P10 | **分账**（AA 记账，一笔支出拆给多人） | 聚餐、团建等场景 | 出现多用户诉求但暂不共享账本 |

**P1/P6/P3 会推翻大量现有设计**，真要做时应当重新评估而不是直接开工。

## 主要风险

### 主要风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 低端 Android 上 WebView + AntD 卡顿 | 记账体验不可用 | V2 真机实测；按屏幕降级，不整体重写 |
| 通知权限被厂商 ROM 限制 / Play 审核拒绝 | 自动记账不可用 | V4 验证；保留手动与分享回退；sideload 备选 |
| 手机/平板访问不到「已同步目录」 | 同步不可用 | WebDAV / NAS 适配器；仍不行才做厂商 API |
| 用户丢失恢复码 | 数据永久不可解 | 强制抄写 + 新设备恢复演练 + 界面明确说明无找回 |
| 冲突处理把两个版本都入账 | 重复计钱 | 不变量 8 + 专项测试；同一 `entityId` 只应用一个版本 |
| 设备时钟偏差导致覆盖错版本 | 数字被静默改掉 | 用版本向量而非时间戳排序（不变量 10） |
| 桌面与手机各写一套规则 | 数字分叉 | 共享 `app`/`domain`；跨端测试向量；合并后 `db:verify` 恒过 |
| 容器文件损坏或只同步到一半 | 数据分叉 | 逐条 AEAD + `formatVersion` 校验 + 原子重命名 + 拒绝整批应用 |
| 网盘客户端改写文件导致容器损坏 | 同步不可用 | 临时文件 + 原子改名；校验失败不应用 |
| 容器体积无界增长 | 同步变慢 | S0/S1 接受（个人规模几 MB）；>50MB 才做增量日志（S2） |
| 用户以为「端到端加密」连本地也加密 | 安全预期错误 | 威胁模型写进设置页；本地明文是明确边界 |
| Tauri 包不住 Express + Prisma | PC 端装不起来 | V1 先验证；失败回退到启动脚本 + 浏览器，不硬凑 |
| 「PC 产品完整」被拖成无底洞 | 移动端迟迟不能开始 | §5.2 清单写死范围；清单外的进 §5.4 候选池 |

每个里程碑结束都要能回答四个问题：**这笔钱在 5 个视图里是否一致？断网还能不能记账？
两台设备冲突时会不会重复计钱？换一台空设备能不能恢复出同样的余额？**
